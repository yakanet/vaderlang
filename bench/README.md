# Vader benchmarks

Thirty-one cross-language workloads spanning float CPU, integer CPU, iterator chains, non-tail recursion / call overhead, GC throughput, hash-map build + probe, string-runtime throughput, byte scanning, sorting by hand and through a comparator, array accessors, nested-array indexing, string interning, split / join, float formatting and parsing, trait dispatch, closed-union tag dispatch, captured closures and coroutine resumption, plus four programs taken from an outside suite (plb2, below) — so a perf change in any of those subsystems trips a regression. Thirty carry all four languages; `async_await` carries two, for the reason its row explains.

Every workload lives in its own directory `bench/<name>/` with all four language implementations colocated — `<name>.vader`, `<name>.ts` (`<name>.js` for the plb2 rows), `<name>.go`, `<name>.java` — alongside the compiled artefacts the harness produces.

### Taken from plb2

The four `plb2_*` rows are [plb2](https://github.com/attractivechaos/plb2) (CC0), a suite that implements the same algorithm in every language so that its bottleneck is never in a library, run at the sizes it publishes. The Go, Java and JavaScript programs are plb2's own, copied at commit `1181b3b8`: each file says where it comes from, and only its output differs, one line the harness can match (`plb2_sudoku` folds its solutions into a rolling checksum instead of printing 4 000 grids). The Vader ports follow the Go programs, since Go is the comparison that matters here: a matrix is one flat array as in Go, where plb2's Java and JavaScript use an array of rows, and `plb2_bedcov` sorts with Go's in-place radix sort, where Java calls `Arrays.sort` and JavaScript `Array.prototype.sort`. The JavaScript runs under Bun as written, from `<name>.js`, rather than through a typed rewrite. A run takes one to three seconds, so these rows are capped at five timed runs (`maxRuns` in `bench/run.ts`); at that length the minimum settles within them.

## Implementations

| stack             | entry-point                                       | how it runs                                                |
|-------------------|---------------------------------------------------|------------------------------------------------------------|
| `vader-native`    | `bench/<name>/<name>.vader` → native binary       | `./build/vader build --emit=executable --release`, then exec |
| `bun-ts`          | `bench/<name>/<name>.ts`, else `.js`              | direct `bun` on that file                                  |
| `go`              | `bench/<name>/<name>.go` → native binary          | `go build`, then exec                                      |
| `java`            | `bench/<name>/<name>.java` → `<name>.class`       | `javac --release 25 -d bench/<name>`, then `java -cp bench/<name> <Name>` |

The harness times each invocation with `performance.now()` around a `spawnSync`, so what's measured is the **process wall-clock** — startup, runtime initialization, kernel, I/O, teardown.

A fifth implementation, `vader-vm`, runs only the `vm_*` workloads (see below): its source is `bench/vm/<name>/<name>.vader`, which no cross-language workload has, so its column is empty on those rows. The build step compiles each program to bytecode text once, batched with the other builds (`./build/vader build --emit=bytecode-text -o build/_bench_vm/<name>.virt bench/vm/<name>/<name>.vader`), and the timed run is `./build/vader run build/_bench_vm/<name>.virt`. The Vader parse + typecheck + lower + bytecode pipeline therefore stays out of the measurement: what is timed is the VM loading and running the bytecode, plus process startup.

Java is precompiled in the build phase rather than run via the single-source-file launcher (`java bench/<name>/<name>.java`). The launcher adds ~200 ms per invocation for in-memory source parsing + class load on top of the JVM cold-start floor ; precompiling drops Java's per-run cost to ~30-50 ms which is the JVM startup + cold JIT alone. For steady-state Java throughput (a long-running JVM that has warmed its JIT), Java would land much closer to Go and Vader native ; the bench measures cold script invocations on purpose.

### Build parallelism

Every implementation that needs a build step (`vader-native` via the Vader compiler + `cc`, `go` via `go build`, `java` via `javac`) is batched up-front in a single `Promise.all` so independent compilers use every available core — an implementation with no source for a given workload is dropped before this step. Building every workload's compiled implementations finishes in 1-3 s instead of the 15+ s a serial compile would take.

**Measurements stay strictly serial.** Running two CPU-bound benchmarks concurrently on the same machine corrupts the signal — they steal cycles from each other, contend on L3 + memory bandwidth, and on Apple Silicon shuffle between P/E cores. Wall-clock numbers from parallel measurements aren't comparable across runs, which is exactly the opposite of what a regression-detection bench needs.

## Running the bench

```sh
bun run bench                    # measure + compare to baseline
bun run bench -- --update        # rewrite baseline with current measurements
bun run bench -- --update --workload=plb2_nqueen  # re-record that row, keep the others
bun run bench -- --runs=5         # override the default of 10 timed runs (+ 1 warmup)
bun run bench -- --workload=primes  # narrow to a single workload
bun run bench -- --workload=vm_fib,vm_loop  # the VM rows only
```

The `vm_*` workloads (`bench/vm/`) are sized for the bytecode interpreter, which is
one to two orders of magnitude slower than native code, and only the `vader-vm`
column runs them: `vader run` on a `.virt` compiled once up front, so the timed run
is the VM alone.

Exit status is non-zero if any (workload, implementation) `min(samples)` regresses by more than **15 %** against `bench/baseline.json`, or if any implementation's checksum diverges from its committed baseline.

Regression detection skips samples whose baseline is faster than **5 ms** — OS scheduling noise routinely adds ±1 ms, which exceeds 15 % of a 5 ms sample, so flagging those would just create false positives. Those rows still appear in the output table.

The threshold does not cover everything it should: `binary_trees/go` sits just above it at 5.4 ms and read anywhere from 5.4 to 6.9 ms over four passes of one unchanged build on 2026-10-04, so it trips the 15 % gate on its own noise — it did in one of those four. The Vader column of the same row sat in that spot before it dropped under the floor. Treat a lone `binary_trees` flag as noise until a second pass confirms it. The baseline keeps the number the `--update` run actually measured rather than a hand-picked typical one.

We compare on `min(samples)` rather than the median because these workloads finish in tens of milliseconds — JIT warm-up and GC pauses routinely push the median 15 %+ above the steady-state cost, but the best sample stays close to the actual CPU path.

Reading the table :

- **`mandelbrot`**: Vader native (14.7 ms) beats Go (16.8 ms) and Bun-TS (22.7 ms). After the for-over-integer-range counter-loop lowering (commit `1e268fd3`), the float kernel hits a state where clang `-O3` is doing essentially the same work as `gc`, with a marginal lead from FMA-free arithmetic on this specific kernel.
- **`primes`**: Vader native (23.3 ms) and Go (23.8 ms) run neck-and-neck, both well ahead of Bun (37.7 ms). Trial division is mostly integer modulo; the sub-millisecond gap (whichever way it tips run to run) is startup noise, and Bun's JIT pays an extra dispatch. `-fwrapv` costs Vader about 5 % here: once `d + 2` may wrap, clang can no longer prove the divisor stays positive, so it keeps the division guards inside the inner loop and divides with `sdiv` where it used `udiv`.
- **`iter_chain`**: Vader native (1.7 ms) beats Go's direct loop (2.4 ms) and crushes the unfused generators, Bun-TS (~35 ms) and Java's Stream API (~58 ms), by about 20 × and more. The lowerer detects `for x in (0..<N).filter(is_even).map(square_i64) { … }` (fluent UFCS chain or struct-lit chain, both bottom out at a `RangeExpr`) and collapses the three-level lazy chain into a single counter loop with the `pred` / `f` calls DEVIRTUALIZED to direct calls, so it stays off the 7-23 × slower unfused path (one step through `Iterator.next` per layer per iteration, each one a call the fused form does not make). REGRESSION + FIX (2026-07-16): the `map`/`filter` → `@generator` rewrite (`f2c0fb49f`, bisected) kept the loop fusion but bound the callbacks to fn-value locals called INDIRECTLY through the erased `vader_fn_t` (per-iteration arg boxing + a fn-pointer hop), doubling this to ~4.6 ms. The `devirtualize_fn_refs` lower pass (commit `f231b169b`) restores direct calls (`let f = square_i64 ; … f(x)` and `let f = <lambda> ; … f(x)` are rewritten to call the concrete fn directly), bringing it back to its pre-regression, Go-beating ~2 ms position.
- **`binary_trees`**: Vader native (4.0 ms) leads Go (5.4 ms), both well ahead of Bun-TS (11.2 ms). The 16-byte box took it from 6.2, since a `Node | null` field travels boxed. After the nullable-ref inline representation landed, `Node` dropped from 72 B → 40 B (-44 %) and GC pressure dropped accordingly, putting Vader alongside `gc`'s tracing collector on this allocation-heavy workload. Which of the two carries the ★ flipped between earlier captures (Go led 6.2 to 6.5 on the 2026-09-13 one), when the gap was under 1 ms on a 6 ms sample, inside the ±1 ms scheduling noise this file documents; Vader has led by 1.4 ms in the 2026-10-04 capture and in both of 2026-10-22.
- **`string_builder`**: Vader native (2.9 ms) leads Go (3.9 ms), ahead of Bun-TS (8.5 ms), with Java (54.5 ms) trailing; at this size it sits under the 5 ms regression floor. The Vader `StringBuilder` stores fragment refs in a `string[]` and flushes once via the `Display::to_string` intrinsic (no per-iter copy), where Go's `strings.Builder` writes straight into a `[]byte` and amortises the grow over a single buffer. What Go does not do is intern the result: the flushed 3.6 MB string is hashed whole before it becomes an atom. The hash moving to eight bytes per step (`4bf934004`) cut the row's instructions by 40 % back to back and took it 6.1 → 2.9 ms, past Go. Before that, back to back against `49a14d45a`, the row ran 9.3 % fewer instructions (a ref push storing the raw pointer, `a775e07cd`, measured −1.26 %, and a tail forwarder pushing no GC frame, `0563cb923`, −7.0 %), which the first 2026-10-22 capture barely showed (6.2 → 6.1 ms).
- **`map_iter`**: Vader native (1.6 ms) leads Go (7.7 ms) by ~5 ×, and crushes Bun-TS (31.3 ms) and Java (66.7 ms) ; it read 2.5 ms until an element access stopped re-checking its buffer (`docs/adr/0023`), and at this size it sits under the 5 ms regression floor. Earlier baselines had Vader behind Go (~23 ms, ~2.8 × slower) ; GC + dispatch optims (`O(log N)` string-mark, midir vtable pruning, lower-pass O(1) symbol lookups) first erased the gap, then the compact-dict `MutableMap` rewrite (2026-06) roughly halved it again (6.5 → 3.6 ms). Go's `for k, v := range m` allocates nothing per visit ; Vader's `for entry in m` desugars via `Into(Iterator(Entry(K, V)))` (cf. `std/collections.vader`). `Iterator.next` hands its element back beside a `Continuation` rather than through a heap wrapper, so the dispatch is alloc-free. Bun's `Map[Symbol.iterator]` and Java's `entrySet()` both box per visit.
- **`java`**: most Java rows sit at ~53-116 ms (heavier workloads like `arr_rw`, ~109 ms, add real compute on top), and the whole column moves together between captures (15-63 % slower from 2026-09-14 to 2026-09-24 with nothing changed in the workloads, then −16 to +8 % to 2026-10-04, −12 to +0.5 % to the first 2026-10-22 capture and −1.8 to +4.5 % to the second, on Oracle GraalVM 25.0.4), so compare Java within one capture, never across two. That floor is JVM startup + class loading + cold JIT, measurable but bounded now that we precompile in the build phase (down from ~230 ms when each invocation also parsed the source). For steady-state Java throughput (long-running JVM, warmed JIT, millions of iterations) Java would catch up to Go ; we're benching cold script invocations on purpose because that's what `java <Class>` looks like in practice.
- **`arr_rw` / `arr_push` / `str_concat` / `interp`** (Target-ABI workloads, added after the original six): the Target-ABI paths, now mostly closed. `arr_rw` 56.0 ms vs Go 35.7 (1.6 ×), `arr_push` 7.9 vs Go 31.0 (3.9 × the other way, was 2.0 × behind), `str_concat` 6.2 vs Bun 8.3 / Go 10.7 (the fastest of the four), `interp` 21.9 vs Go 18.2 (1.2 ×); Vader is ahead of Bun (40.6) on `interp` (the workload gained an emoji + codepoint-count checksum, so it is not comparable to the pre-2026-07 `interp` numbers). They exercise the open-coded array load/store, the push/grow + young-arena GC churn, and the off-runtime Buffer-backed string `+` concat / `${}` interpolation paths. **`arr_rw`** dropped from a midir intra-block array-load-forward pass (drops the redundant re-read in `a[i] = a[i] + 1`, commit `6fc1def1`) plus a native c_emit resolve-CSE that shares the buf-forward walk across accesses in one straight-line region (`0af7deb9`). The walk itself then went: no header points at a moved buffer any more, so an element access stopped re-checking for a forward (`docs/adr/0023`), and the row dropped 57.7 → 34.5 ms, level with Go, then rose to 55.2 ms on 2026-10-10 with `-fwrapv`: once `a[i] + 1` may wrap, clang folds its `i32` to `i64` extension into the loop-carried `sum` add, a slower instruction on Apple cores (`docs/HISTORY.md`, "Signed overflow"). Go has the same wrapping semantics but emits the extension as its own instruction, off that chain. **`interp`** dropped earlier because a `${int}` now writes its digits straight into one exact-sized byte buffer instead of minting a throwaway interned string per part (`2e294f5c`). It dropped again in the second 2026-10-22 capture, 26.4 → 21.9 ms: the interpolated result is still interned, and the atom hash moving to eight bytes per step (`4bf934004`) took 8.6 % of the row's instructions back to back; the rest of the wall-clock move is not traced. **`str_concat`** went 21.5 → 8.2 ms on 2026-09-13, a 2.6 ×, and took the row: it had been the one workload of the sixteen where Bun beat Vader. Three lowering changes, in the order they compound. A `+` chain's adjacent literal leaves now merge before the arity is chosen, so an all-literal chain emits no call at all and a mixed one loses the arity its literal runs cost. Consecutive `s = s + …` appends then fuse into a single `concat_N`: building a string in k steps used to cost k buffers and k interns, and the intermediate results were all discarded. Finally `concat_N` calls the `Buffer` impl members directly rather than `new_byte_buffer` / `finish_buffer`, two one-line free wrappers that each pushed and popped a GC shadow-stack frame `cc` cannot elide (the collector reads `vader_gc_top`). The fusion carries the row (2.3 × of the 2.6 ×) and the wrapper change adds 3.4 %. The second 2026-10-22 capture took it 7.1 → 6.2 ms: each `concat_N` interns its result, and the atom hash moving to eight bytes per step (`4bf934004`) took 10 % of the row's instructions back to back. The one measured lever left on this path is the `memset` in `vader_buffer_new`, worth ~4 %: `concat_N` overwrites every byte it allocates, but `BufferAlloc.new_buffer` is a public API whose caller may read a byte it never wrote, so eliding it safely needs a second, uninitialised allocation reachable only from the paths that provably fill everything. **`arr_push`** went 49.3 → 13.6 ms on 2026-09-14 and took the row from Go (31.5), which it leads by 3.9 × in the 2026-10-22 capture. Two later changes are traced: an array a counted loop fills is created at its trip count (`68ba78b1b`, −14 %), and the young halves swap only when to-space receives survivors (`95052cce9`, `docs/adr/0107`, −13 % back to back), about half of this capture's 10.4 → 7.9 ms; the rest is not traced. (Until this capture it had read anywhere from 10.4 to 15.5 ms across captures: its loop pushes `i32` into a PACKED array and never touches a box, so it moved with the runtime's code layout rather than with anything semantic. `-falign-functions=64` is in the tree to damp exactly that.) It had been the workload where the two-level `vader_array_t → vader_array_buf_t` representation cost the most: a push reloaded the header, the buffer pointer, the length and the capacity every iteration, because nothing tells `cc` the call cannot move them. Go's slice is a value in registers ; ours is two indirections. A loop whose only use of an array is pushing to it can hold that state in four locals and commit `length` at the exit: 18 instructions, 6 loads and 3 stores per push become 6, 0 and 1. The analysis is a LOWER pass (`vader/lower/push_cache.vader`), not a backend one: it marks `LoweredArrayPush.cached` where the lift is sound and the marker rides through midir and the bytecode as `ArrayPush.cache_slot`, so a second backend inherits the proof instead of re-deriving it. The emitter re-checks it against the op stream it actually ships, which is the half that matters: midir and the bytecode passes have their say after the proof, and a module const materialised into the slot inside the loop is visible only there. First cut is narrow: packed element kinds only, one array per loop, no nested loops. Before that it had dropped 66 → 49 ms once `push` on a statically-primitive array stopped boxing + calling the generic runtime append and started emitting a typed `vader_array_push_<kind>` inline (typed store at the tail, no box / kind dispatch / write barrier), one helper per primitive width, full parity with the indexed-store path. It still keeps the `-falign-functions=64` cache-line fix (commit `7a96cc48`) that undid a layout-only regression.
- **`arr_set`**: the same read-modify-write as `arr_rw`, but bounded by `for i in 0..<a.len()` instead of a separate `n`. The bound is read once, before the loop. In a release build the range analysis proves `i < a.len()`, so the body's `a[i]` carry no bounds check (`docs/adr/0058`). An element access carries no buffer resolve (`docs/adr/0023`), so nothing in the body keeps clang from treating `a->buf` as loop-invariant.
- **`arr_map`**: Σ `square(a[i])` driven through **each language's idiomatic map abstraction**, not a hand loop: Vader's fused `for x in a.map(square)`, JS's eager `a.map(x => x * x).reduce(…)`, Java's `Arrays.stream(a).mapToLong(…).sum()`, Go's `iter.Seq` range-over-func (1.23+). The Vader lowerer fuses `a.map(f)` into a plain `a[i]` counter loop calling the callback (no per-element iterator step: fused *array* iterators are alloc-free, unlike opaque ones), and in a release build the range analysis (`vader/midir/ranges/mark.vader`) proves the synthesized `a[i]` in range, so it drops its bounds check. Vader native (**17.3 ms**) is the *fastest* by a wide margin: **4.9 × Go** (85.3 ms ; its range-over-func inlines well but keeps per-access bounds checks and doesn't vectorise the dependent sum), **11 × Java** (186.1 ms, JIT'd Stream), **27 × Bun** (464.6 ms, the eager `.map()` allocates a 1024-elt array every pass) : Vader's is the only map that fully fuses to zero cost. The proof names no combinator: any callback qualifies unless it may shorten an array. 3 × `arr_set`'s pass count so the fused Vader path clears the ~5 ms noise floor and stays regression-gated.
- **`arr_collect`**: the chain `arr_map` consumes by a `for`, drained into an array instead, through each language's idiomatic pipeline: Vader's fused `a.filter(is_odd).map(square).collect()`, JS's eager `a.filter(isOdd).map(square)`, Go's `iter.Seq` stages into `slices.Collect`, Java's `Arrays.stream(a).filter(…).mapToLong(…).toArray()`. The fused loop pushes into an accumulator the lowering minted, and the push cache (`vader/lower/push_cache.vader`) holds its length / capacity / slots in locals, as for a hand-written push loop; the row read ~57 ms before the cache accepted a fused `collect`. The fused source read has no bounds check in a release build: a push only grows an array, so the range analysis keeps the length it knows across it. Vader (25.3 ms) leads Go (64.6 ms) by 2.6 ×; it read 33.6 ms in the 2026-10-04 capture; the young halves swapping only when to-space receives survivors (`95052cce9`) took 7.8 % off it back to back, and the rest of the drop is not traced.
- **`hashmap`**: Vader native (13.4 ms) is the *fastest*, **3.2 × Go**'s built-in `map` (43.2 ms) and ~8.4 × faster than Bun (112.7 ms). It read 27.2 ms until two changes: an element access stopped re-checking its buffer for a forward (`docs/adr/0023`, −28 % back-to-back), and a collision started folding five more bits of the hash into each probe step (`f487c431d`, −13 %), so the runs that `remove`'s tombstones used to merge into long ones stay short. The first 2026-10-22 capture took it from 16.0 ms, each step measured back to back: no index check per `put` and one probe per set add (`f81a2c444`, −7.5 %), `write_entry` folded into `put` (`6884e0810`, −6.3 %), a tail forwarder that pushes no GC frame (`0563cb923`, −3.8 %), then `put` growing only on insert and the growth threshold kept with the index (`87e9ccc7b`, `616b8e899`, −0.8 % each). The compact-dict `MutableMap` (open-addressed `i32` index over dense entry arrays, cf. `map_iter`'s note) absorbs the insert / lookup / delete / grow churn with no per-op allocation ; this is the build-and-probe counterpart to `map_iter`'s pure iteration, and the shape a compiler's symbol table / interner actually sees. All four maps grow from empty (no port pre-sizes), so the row measures the rehash / grow path it advertises, not just steady-state probing. Keys are `(i·STRIDE) mod KEYSPACE` with STRIDE coprime to the prime KEYSPACE, so all 100 000 keys are distinct and the set is identical across ports.
- **`ackermann`**: pure non-tail recursion, zero allocation, isolating the raw call path (prologue / epilogue, argument passing, direct-call dispatch) the way `binary_trees` (allocation-dominated) can't. Vader native (37.2 ms) lands level with Go (39.3 ms) and Bun (42.5 ms), ahead of Java's JVM-startup floor (70.7 ms). At this size a large share of the wall-clock is process startup (Vader's is ~0), so like `iter_chain` this row stays startup-sensitive ; the *pure* per-call overhead only separates the field at far larger n: `A(3,11)` is ~10 × the calls, and there Vader native is the **slowest** (a real gap), but that would blow the suite's tens-of-ms budget, so we size down to `A(3,9)`.
- **`wordcount`**: byte-scan / tokenize, the inverse of the string-*building* rows. Vader native (7.3 ms) is the *fastest*, **3.3 × Go** (24.3 ms) with its `[]byte` range loop, and well ahead of Bun (40.9 ms) and Java (77.8 ms). Part of each run builds the buffer: `repeat` produces one 1.76 MB string, interned and so hashed whole, and the atom hash moving to eight bytes per step (`4bf934004`) took 8.3 % of the row's instructions back to back (8.8 → 7.3 ms across the two 2026-10-22 captures). It was 39.5 ms before the dominance resolve-CSE (2026-07-28) and 25.5 ms just after. The rest of the drop happened between that capture and the 2026-09-13 one, and this file did not track `bench/baseline.json` across the 2026-08-30 rebaseline in between, so no single landing is claimed for it here. The workload itself has not moved since 2026-07-19, so the figures are comparable. The scan loop is `no_frame`, and its whitespace state machine branches on every byte, so under the old rule each `If` dropped the cache and the very next `u8[]` load re-resolved the buffer ; the resolve now survives into the branch arms. Vader scans the zero-copy `bytes()` view through the open-coded `u8[]` load: the lexer's inner loop, which nothing else in the corpus measures. What's left of the gap is the branch-heavy state machine, not the load (per the u8-read note, `cc -O3` already erases the per-byte tax).
- **`quicksort`**: array get/set + swaps + bounded recursion, the *same* hand-written median-of-three Lomuto sort in every language (not the stdlib), so it compares codegen rather than library quality. Go (33.6 ms) leads by a nose, Vader native (36.5 ms) is a close second, ahead of Bun (73.7 ms) and Java (107.7 ms). **Was 49.2 ms (1.4 × Go) until the dominance resolve-CSE landed (2026-07-28), a 23 % drop.** The partition loop is a `no_frame` fn (provably no-alloc, so no GC safepoint can move a buffer anywhere in its body), which now lets a resolved buffer survive *entering* a nested scope (`Block`/`Loop`/`If`) instead of being dropped at every control-flow op (`invalidate_header_cache`, `vader/emit/c/walker.vader`). The partition's compare/swap arms each re-resolved the same array before ; they now share one resolve per iteration. Exercises the swap / reassign lowering (a former miscompile site) and the typed `a[i]` store ; the input is a coprime-stride permutation of [0, N) so the sorted result is exactly [0, N) and the order-sensitive rolling-hash checksum proves the sort ran. Recursing the smaller half bounds the stack to O(log N).
- **`wordfreq`**: Go (9.9 ms) leads, Vader (11.9 ms) is 1.2 × behind, ahead of Bun (33.4 ms) and Java (88.8 ms). Slicing a token out of a byte corpus makes a *fresh* string, and in Vader a string IS an atom (`vader_string_t` is a `u32`), so `bytes_to_string()` has to hash the bytes and probe the global atom table before the map ever sees the key. A cut of the workload in three, taken when the whole of it read **22.2 ms**, said where the time went: corpus build + slice alone was **6.7 ms**, adding `bytes_to_string()` took it to **15.8 ms**, and adding the map to **22.2 ms**, so the interning step cost **9.1 ms** and the map step **6.4 ms**. **The gap was the interning, which Go does not have at all**: a Go string is a pointer and a length. It is a deliberate trade: that one hash is what makes `==` a single integer compare everywhere else in the language, and it dedupes 98.6 % of the 300 000 slices down to 4 096 atoms. The row read 19.7 ms in the 2026-10-04 capture; the collections and forwarder changes took about 15 % off it, compounded from back-to-back pairs (`f81a2c444`, `6884e0810`, `0563cb923`, `87e9ccc7b`), the rest of the drop to 12.2 ms in the first 2026-10-22 capture is not traced, and the cut has not been redone, so it does not say how the remaining 1.2 × splits. The vocabulary is rendered once and both the corpus and the checksum read it back; rendering on demand did the base-26 division 74 times per distinct word, which was over half the Bun-TS column and none of what the row is named for.
- **`shapes`**: Vader (10.4 ms) is the *fastest*, 2.9 × Go (29.7 ms) and ~4.0 × Bun (41.2 ms), with Java (70.5 ms) trailing; it read 18.4 ms in the 2026-10-04 capture, and the drop is not traced. This is the counterpart to `iter_chain`: there the lowerer proves the callee and the call disappears, here it cannot and the call has to happen. Vader's trait dispatch is **not a function-pointer vtable**: emit generates one dispatcher per trait method that switches on the receiver's box tag (`vader_vt_Shape__area`, a `switch (recv.tag)` over the three impls), which `cc` compiles to a dense jump the predictor handles well; Go's is an indirect call through the itab. That is why the row tips this way, and it is also what the row does *not* prove: a switch is O(impl count) where an itab call is O(1), so a trait with many impls would narrow or reverse it. Three impls, cycled so no two consecutive elements share a receiver type, is what is pinned here; a monomorphic inline cache would miss on every third element, which is the point.
- **`tree_eval`**: Vader (38.6 ms) is the *fastest*, ahead of Go (51.1 ms), and well past Bun (116.0 ms) and Java (104.6 ms). It was 1.4 × BEHIND Go until `vader_box_t` went from 24 bytes to 16: the walk passes a box per recursive call, and at 24 bytes that was three loads, three stores and a pointer setup where Go's 16-byte interface is two register moves. The row is what found that, and the disassembly of `main_evaluate` is what said it; two earlier hypotheses died first, including hand-patching the emitted `if` chain into a real `switch`, which moved nothing. A four-variant `match` over a closed union, on a tree built once and walked forty times, so the allocation amortises out and what remains is the tag dispatch plus the recursion. `binary_trees` conflates the two (its walk is a single pass over what it just allocated, and its match has two cases), and `selfcompile_c` runs this shape constantly but only reports it as a 2.2-second aggregate that cannot localise a regression. This is the compiler's own inner loop, and the row exists so a change to how a union carries its tag, how `match` lowers a four-way dispatch, or how each arm gets its field offsets has somewhere cheap to show up. Every operation is additive, so the value stays exact in an f64 mantissa and the four ports agree on the checksum bit for bit.
- **`matmul`**: Go (13.5 ms) leads and Vader (23.0 ms) is 1.7 × behind, ahead of Bun (38.9 ms) and Java (70.7 ms) ; it was 2.1 × until an element access stopped re-checking its buffer (`docs/adr/0023`). A second dimension is not more of the first: a row is its OWN `vader_array_t`, so `right[k][column]` walks two headers and two buffers where a 1-D access walks one, and the inner loop does that on every iteration. `left_row` is hoisted by hand in all four ports so the row measures the indexing rather than the loop shape. Go's `[][]int64` pays one indirection too (its rows are slices, not a flat block), so the gap is ours to explain and this row is where it will show up.
- **`closures`**: Vader (21.7 ms) and Go (21.0 ms) are level, Go ahead by 0.7 ms, with Bun at 41.9 ms and Java at 73.8 ms; it read 25.9 ms (1.2 × behind Go) in the 2026-10-04 capture, and the drop is not traced. The ★ went back to Go between the two 2026-10-22 captures (20.6 → 21.7 ms), but back to back the row executes the same instruction count across that interval: wall noise. It was **3.5 ×** behind and behind Bun too until the box shrank to 16 bytes: a closure's captured value travels boxed, so this row moved for the same reason `tree_eval` did. Two costs are stacked on purpose. A capture that is MUTATED forces the local into a heap cell, so `counter = counter + 1` under a lambda becomes a load, an add and a store through a pointer where outside one it is a register. Then 500 closures are called round-robin, each with its own environment, which keeps the call site megamorphic and mints one allocation per closure. `iter_chain` and `arr_map` both exist to show the lowerer DELETING this indirection, and `devirtualize_fn_refs` removes it wherever the callee is statically known: this row is what is left when it cannot be.
- **`fmt_float`**: Go (5.5 ms) leads by **1.3 ×** over Vader (7.0 ms), with Bun (11.6 ms) behind and Java at 68.3 ms. It read 40.4 ms and was the widest gap in the corpus until 2026-09-14. `interp` covers integer formatting, which writes its digits straight into a byte buffer; a float goes through Ryū (`lib/std/core/dtoa.vader`), several hundred lines of pure Vader that no benchmark had ever exercised. Two files this note used to name alongside it are NOT on the measured path: `f2s.vader` is the f32 formatter, and `bigint.vader` runs under `@comptime` to build the power-of-5 tables; at runtime it serves only `parse_float`. A profile put the cost nowhere near that arithmetic: the whole Ryū core, `mul_shift_all_64` included, was **3 %** of the row, while interning, the array pushes, the concatenations and the atom table's `memcmp` / `memcpy` (all of them the presentation layer turning digits into a string) came to **68 %**, before counting its share of `vader_gc_alloc`. `digits_of` minted a `string[]` of one-char interned atoms and `join_range` then concatenated them one at a time, so a 17-digit rendering cost two growable arrays and one atom intern per digit, each of those interns hashing a prefix that was thrown away one concatenation later. It now writes into a single right-sized `Buffer` and interns once, the shape `format_unsigned` has used since the Target-ABI work: **40.4 → 9.6 ms, a 4.2 ×**, byte-for-byte identical to the old code over 408 055 renderings across all four `Number::toString` branches, with no `vm.snapshot` in the corpus moving. What is left is the string model, not the formatter: holding the rendered length fixed and dropping only the final `intern_string` takes 600 k values from 91.0 to 31.1 ms, so **two thirds of the remainder is turning 17 bytes into an interned atom**: a hash over the content (FNV-1a-64 when that was measured, eight bytes per step since `4bf934004`, which took 3.7 % of the row's instructions back to back), a probe, a `malloc` and a `memcpy`, for a string this workload never compares to anything. Go's `strconv` hands back a `(ptr, len)`. That is the price of `==` being an integer compare everywhere else, and the same tax `wordfreq` and `split_join` pay. The one Vader-side item left is elsewhere again: `mul_shift_all_64` returns a 24-byte `[u64, u64, u64]`, over the value ABI's 16-byte limit, so it is still a heap object the call site destructures on the very next line and never lets escape. `umul128`'s `[u64, u64]` has crossed by value since PR #12 (9.6 → 8.7 ms on this row, `parse_float` moving the same way). Multiples of the divisor are skipped because Vader and Java print `1.0` for an integral value where Go and JS print `1`, a difference of convention, not of work, and the four ports agree byte for byte on everything else (verified, not assumed). Values stay inside [1e-3, 1e5) so no port switches to exponential notation; Java crosses over at 1e7, which makes the window Java's.
- **`async_await`** (two columns): Vader (25.7 ms) is 2.7 × faster than Bun (69.4 ms). Every await is on an already-settled value, so nothing parks on a scheduler and nothing waits on a timer: what is measured is the block-split lowering and the frame that carries locals across a suspension point. **Go and Java are deliberately absent.** Go has no async/await, and its nearest idiom (a goroutine and a channel round-trip) parks on the scheduler, which is a different and far heavier thing; Java is the same story with virtual threads. Those rows would report which concurrency model is cheaper rather than whether our coroutine lowering regressed, which is not what this corpus is for. The harness drops an implementation whose source file is absent, so the two columns are simply empty.

- **`parse_float`**: Bun, Go and Vader are level at 22.4, 23.2 and 24.1 ms, and Java trails at 107.9 ms. Vader was 1.3 × behind (32.8 ms) until small composites started crossing calls by value (PR #12): `pf_product` returns a `[u64, u64]`, and that pair used to be a heap object the caller destructured on the next line. Read this row NEXT TO `fmt_float`: they are the two directions of one subsystem, both pure Vader. Decimal → f64 is level now; f64 → decimal was 6.9 × off and is 1.3 × now. The pair did its job: it said the cost was on the rendering side and not in float handling generally, which no single row could have said. What it could not say is WHICH half, and this file guessed Ryū and the big-integer kernel under it; a profile then put the Ryū core at 3 % and the big-integer kernel nowhere at all, because it does not run on this path, while the digits-to-string layer sitting after Ryū was over 80 %. A pair of rows narrows the search, a profile ends it. `parse_float` also used to be `strtod` natively and a naive accumulator on the VM, and the two disagreed on real inputs; one implementation now serves both, so nothing but this row will notice if it regresses. The checksum sums the two halves of each result's bit pattern, which is what correct rounding means and what a value-level sum would blur.
- **`sort_by`**: Vader (21.9 ms) is the *fastest*, **2.8 × Go** (60.6 ms), 3.3 × Bun (72.9 ms), with Java at 118.0 ms; it read 29.4 ms until an element access stopped re-checking its buffer (`docs/adr/0023`). Distinct from `quicksort`, which hand-writes a monomorphic partition and compares codegen: this one calls `std/sort`'s merge sort through a fn value, so it measures the library plus one indirect call per comparison, which is the shape `sort(items, by_name)` actually takes. `devirtualize_fn_refs` turns that fn value into a direct call, which is most of the lead. Go's `slices.SortStableFunc` and Java's TimSort both keep the indirection; Java additionally boxes, since `Arrays.sort(long[])` takes no comparator. The comparator orders on a derived key so equal keys are common, and the checksum reads their order back, which is why every port uses its STABLE sort.
- **`split_join`**: Go (8.3 ms) leads by **1.6 ×** over Vader (13.6 ms), which is now ahead of Bun (16.7 ms); Java is at 79.5 ms. It read 30.0 ms (3.7 × behind Go, and behind Bun) in the 2026-10-04 capture and 14.5 ms in the first 2026-10-22 one; of that drop only a ref push storing the raw pointer (`a775e07cd`, −2.45 % instructions), a tail forwarder pushing no GC frame (`0563cb923`, −2.9 %) and the atom hash reading eight bytes per step (`4bf934004`, −1.5 %, each part being interned) are traced. The gap is representational, and it is the same one `wordfreq` measures from the other side: `strings.Split` hands back slices that SHARE the original string's bytes, so Go allocates nothing per field and copies nothing, while a Vader part is a fresh interned atom (hashed, probed, and stored). That buys `==` at one integer compare everywhere else in the language, and this is a row where the bill arrives. None of the other string workloads cut a string into an array: `str_concat` grows one string, `string_builder` appends fragments, `wordcount` scans bytes without producing any, `wordfreq` slices at computed offsets.
- **`plb2_*`** (see *Taken from plb2*): Go is the comparison these rows were added for, and the Vader ports do its work line by line. `plb2_nqueen`, integer and bitmask work only, puts all four within 15 %: Bun 2.22 s, Go 2.27, Java 2.36, Vader 2.56 (1.13 × Go). `plb2_sudoku`, an exact-cover search over small integer tables, has Go ahead at 1.71 s, then Java at 1.87, Vader at 2.22 (1.30 × Go) and Bun at 2.42. The other two rows are where Vader is furthest from Go. `plb2_matmul` reads 2.14 s against Go's 0.94 (2.3 ×), with Java leading at 0.67 and Bun at 2.00. The Vader port holds a matrix in one flat `f64[]` as Go does, and binds its arrays to locals before the loops as Go slices its rows, so the gap is Vader's own; it is not traced yet. `plb2_bedcov` reads 1.46 s against Go's 0.65 (2.2 ×). Go keeps its intervals as 32-byte values in one array, while Vader, Java and JavaScript hold references to objects on the heap, and those three columns land together, from 1.46 to 1.67 s; whether the references account for the whole gap is not measured.

- **`selfcompile_c`** (Vader-only, compile-time): times the compiler emitting C for the whole compiler. **2.22 s** in the second 2026-10-22 capture, after the atom hash moved to eight bytes per step (`4bf934004`, −1.3 % instructions back to back, −1.9 % on one input with no collection running); the rest of the 2.43 → 2.22 s move is not traced. The first capture of the day read 2.43 s, down from 2.84 s on 2026-10-21, through changes each measured back to back against the commit before it. In the runtime: a young survivor is promoted at its first minor (`51616b387`, `docs/adr/0104`, −8.9 % wall), a major leaves the card table as its minor left it (`3ba8b067d`, `docs/adr/0105`, −6.3 % instructions), a boxed push stores in place without a call (`8465d1a07`, −2.5 % instructions), and the young halves swap only when to-space receives survivors (`95052cce9`, `docs/adr/0107`, −3.7 % wall, peak RSS 1 525 → 1 032 MB). In the C emitter: emitter fixes (`f20696a3e`, −4.7 % instructions), a ref push stores the raw pointer (`a775e07cd`, −2.1 % wall), and a tail forwarder pushes no GC frame (`0563cb923`, `docs/adr/0106`, −1.3 % wall). In `std/collections` and its callers: the `put` and set-add changes (`f81a2c444`, `6884e0810`, −0.7 % and −0.96 % instructions), then the compiler's own lookup-then-insert sites moved to `get_or_put` (`161fedaf5`, −0.65 to −1.05 % instructions, measured with a young generation large enough that no collection runs). Taken one at a time they compound to more than the row moved: some are wall-clock and some instruction counts, and the tree being compiled grew with each commit. Two caveats hold for this row. It compiles the compiler's own tree, which grows with every change, so it drifts up between captures with nothing getting slower. And at this capture it sits near a major-collection threshold: one more major collection swings it by about 5 %, so a move of that size needs a back-to-back pair before it means anything. Earlier, it had read 2.97 s on 2026-10-10, up from 2.26 s on 2026-10-04: deducing a parameter's `!` (`docs/adr/0051`) ran the typecheck in rounds, each a full pass over the bodies, and cost 22 % on its own (bisected), until mutable by default (`docs/adr/0053`, carried out by 0067 and 0069) removed those rounds (2.84 s on 2026-10-21). The compiler has grown since 2026-10-04, and the gap to 2.26 s is not traced. The 2.26 s was down from 4.12 s on 2026-09-24, through three changes to the front end's hot paths: a span key goes through a real mix before it slots into a map (`ceea7c502`, the typecheck 810 → 520 ms), a collision folds the hash's high bits into the probe (`f487c431d`, typecheck −14 %), and an element access stopped re-checking its buffer (`docs/adr/0023`, −19 % on this row back-to-back). The 4.12 s was itself roughly half the 8.7 s of an earlier baseline: the 2026-07-16 fix that stopped the single-expression inliner from splicing statement-bearing trait-method bodies (e.g. an enum's `= match self { … }`) removed a pathological inline explosion in the compiler's own code (one diagnostic snippet's bytecode collapsed 13818 → 129 lines), so there is far less C to emit ; the `devirtualize_fn_refs` pass shaves a little more.

The `mandelbrot` checksum splits three ways : Bun-TS / Java agree at 5 705 453, Vader-native lands at 5 705 449 (a 4-iteration drift, ~7 boundary pixels where clang's reassociation under `-O3` reorders a `z² + c` term and flips the escape test one iteration earlier), and Go lands at 5 689 008 because `gc` fuses `a*b + c` into a single FMA instruction with one rounding step on arm64. All three are mathematically correct ; only the rounding model differs.

## Adding a workload

1. Write the kernel in `bench/<name>/<name>.vader`. Print a one-line checksum to stdout.
2. Port it to `bench/<name>/<name>.ts`, `bench/<name>/<name>.go`, `bench/<name>/<name>.java` — all colocated in the same directory. Keep the algorithm bit-identical (the harness verifies checksum equality against the committed baseline). A port may be omitted : the harness silently drops any implementation whose source file is absent, so a Vader-only workload still works (its row just shows only the `vader-native` column).
3. Add an entry to `WORKLOADS` in `bench/run.ts`.
4. Add the Vader binary line `bench/<name>/<name>` to `.gitignore` ; the `.c`, Go binary and `.class` artefacts are already covered by the `bench/*/*.c`, `bench/*/*_go`, `bench/*/*.class` globs.
5. Run `bun run bench -- --update` to extend the baseline (baselines are machine-specific — a new workload simply isn't regression-gated until someone records it on the canonical machine).

## Caveats

- The natively-compiled Vader path uses `--release`, which sets `-O3 -DNDEBUG` and post-link `strip`. Compiler is the system `cc` (clang on macOS, gcc on Linux).
- Bun's measurement of process wall-clock includes its own startup, measured at 11.4 ms on macOS with an empty script. On a workload that takes 15 ms total that is two thirds of the run, so read every `bun-ts` row under ~15 ms (`str_concat` 8.3, `string_builder` 8.5) as mostly startup rather than as a measurement of the language's throughput. The same caveat applies to Java, at a much larger floor (see its bullet above).
- The `vader-vm` numbers time `./build/vader run` on a `.virt` the build step compiled beforehand, so the timed run is the VM alone (process startup, loading the bytecode, executing it), without the Vader parse + typecheck + lower + bytecode pipeline.
