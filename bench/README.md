# Vader benchmarks

Twenty-six cross-language workloads spanning float CPU, integer CPU, iterator chains, non-tail recursion / call overhead, GC throughput, hash-map build + probe, string-runtime throughput, byte scanning, sorting by hand and through a comparator, array accessors, nested-array indexing, string interning, split / join, float formatting and parsing, trait dispatch, closed-union tag dispatch, captured closures and coroutine resumption — so a perf change in any of those subsystems trips a regression. Twenty-five carry all four languages; `async_await` carries two, for the reason its row explains.

Every workload lives in its own directory `bench/<name>/` with all four language implementations colocated — `<name>.vader`, `<name>.ts`, `<name>.go`, `<name>.java` — alongside the compiled artefacts the harness produces.

| workload         | exercises                                       | algorithm                                                       | scale                                  |
|------------------|-------------------------------------------------|-----------------------------------------------------------------|----------------------------------------|
| `mandelbrot`     | f64 arithmetic, tight loop                      | per-pixel iteration of `z := z² + c` until escape or cap        | 240 × 180 grid, max 500 iter per pixel |
| `primes`         | i32 / i64 arithmetic, modulo                    | count primes ≤ N by trial division up to `√n`                   | N = 1 000 000                          |
| `iter_chain`     | lazy iter dispatch, per-iter union allocation   | Σ x² for even x in [0, N) via `Range.filter(p).map(f)` chain    | N = 1 000 000                          |
| `binary_trees`   | recursive allocation + GC throughput            | build a balanced tree, then count its nodes                     | depth = 17 (262 143 nodes)             |
| `string_builder` | string runtime + GC under in-flight builder     | append a 45-char fragment N times, finalise to a flat string    | N = 80 000                             |
| `map_iter`       | hash-map entry iteration, per-visit alloc       | 1 000 outer × 1 000 inner `for entry in m` over a 1 000-entry map | 1 M map visits total                 |
| `arr_rw`         | array element get/set, no allocation            | `a[i] = a[i] + 1` over a fixed buffer (open-coded typed load/store) | 1024-elt `i32[]`, 100 000 passes     |
| `arr_set`        | indexed r-m-w bounded by `a.len()` (BCE)        | same as `arr_rw` but `for i in 0..<a.len()` — BCE hoists the buf resolve | 1024-elt `i32[]`, 100 000 passes  |

| `split_join`     | `split` into an array, filter, `join` back       | cut a 20 k-field line, keep the odd-length pieces, rejoin them          | 20 k fields × 24 passes       |

Every program prints a one-line checksum so cross-language equivalence is verifiable.

## Implementations

| stack             | entry-point                                       | how it runs                                                |
|-------------------|---------------------------------------------------|------------------------------------------------------------|
| `vader-native`    | `bench/<name>/<name>.vader` → native binary       | `./build/vader build --emit=executable --release`, then exec |
| `bun-ts`          | `bench/<name>/<name>.ts`                          | direct `bun bench/<name>/<name>.ts`                        |
| `go`              | `bench/<name>/<name>.go` → native binary          | `go build`, then exec                                      |
| `java`            | `bench/<name>/<name>.java` → `<name>.class`       | `javac --release 25 -d bench/<name>`, then `java -cp bench/<name> <Name>` |

The harness times each invocation with `performance.now()` around a `spawnSync`, so what's measured is the **process wall-clock** — startup, runtime initialization, kernel, I/O, teardown.

A fifth implementation, `vader-vm` (`./build/vader run bench/<name>/<name>.vader`), exists in the codebase but is commented out in `bench/run.ts`'s `IMPLS` list. Reason : each VM invocation pays 2-30 s for the Vader parse + typecheck + lower + bytecode pipeline, which dwarfs the actual VM loop. Including it inflates the total bench wall time from ~6 s to ~5 min without surfacing a regression signal that `vader-native` doesn't already cover. Uncomment the entry when a change targets the VM exec path specifically (e.g. once the bytecode-on-disk cache lands and the compile phase is amortised).

Java is precompiled in the build phase rather than run via the single-source-file launcher (`java bench/<name>/<name>.java`). The launcher adds ~200 ms per invocation for in-memory source parsing + class load on top of the JVM cold-start floor ; precompiling drops Java's per-run cost to ~30-50 ms which is the JVM startup + cold JIT alone. For steady-state Java throughput (a long-running JVM that has warmed its JIT), Java would land much closer to Go and Vader native ; the bench measures cold script invocations on purpose.

### Build parallelism

Every implementation that needs a build step (`vader-native` via the Vader compiler + `cc`, `go` via `go build`, `java` via `javac`) is batched up-front in a single `Promise.all` so independent compilers use every available core — an implementation with no source for a given workload is dropped before this step. Building every workload's compiled implementations finishes in 1-3 s instead of the 15+ s a serial compile would take.

**Measurements stay strictly serial.** Running two CPU-bound benchmarks concurrently on the same machine corrupts the signal — they steal cycles from each other, contend on L3 + memory bandwidth, and on Apple Silicon shuffle between P/E cores. Wall-clock numbers from parallel measurements aren't comparable across runs, which is exactly the opposite of what a regression-detection bench needs.

## Running the bench

```sh
bun run bench                    # measure + compare to baseline
bun run bench -- --update        # rewrite baseline with current measurements
bun run bench -- --runs=5         # override the default of 10 timed runs (+ 1 warmup)
bun run bench -- --workload=primes  # narrow to a single workload
```

Exit status is non-zero if any (workload, implementation) `min(samples)` regresses by more than **15 %** against `bench/baseline.json`, or if any implementation's checksum diverges from its committed baseline.

Regression detection skips samples whose baseline is faster than **5 ms** — OS scheduling noise routinely adds ±1 ms, which exceeds 15 % of a 5 ms sample, so flagging those would just create false positives. Those rows still appear in the output table.

The threshold does not cover everything it should: `binary_trees/vader-native` sits just above it at 5.4 ms and measured 5.6, 5.7 and 6.9 ms over three later passes of the same build, so it trips the 15 % gate on its own noise perhaps one run in three. Treat a lone `binary_trees` flag as noise until a second pass confirms it. The baseline keeps the number the `--update` run actually measured rather than a hand-picked typical one.

We compare on `min(samples)` rather than the median because these workloads finish in tens of milliseconds — JIT warm-up and GC pauses routinely push the median 15 %+ above the steady-state cost, but the best sample stays close to the actual CPU path.

## Baseline (committed)

Captured 2026-09-14 on a 2026 Apple Silicon laptop, `bun bench/run.ts --update --runs=40`, after `vader_box_t` went from 24 bytes to 16 (`docs/adr/0018-*`), after a review pass fixed three workloads that were measuring their own bookkeeping, after three more were added — `parse_float`, `sort_by`, `split_join` — and after the f64 presentation layer stopped assembling its result one interned atom per digit (see the `fmt_float` note, 40.4 → 9.6 ms).

Two of those fixes move a column a long way and are worth naming, because the old numbers understated Vader's gap rather than flattering it. `fmt_float`'s checksum did an i64 modulo per emitted character — 90 % of the Bun-TS column, so the row compared hashing, not rendering; a position-weighted sum replaces it and Bun drops 30.4 → 12.4 ms, with the Vader-to-Go ratio of that day widening from 5.5 × to 6.9 × (it is 1.7 × now, for a reason the row's own note gives). `wordfreq` rendered each of its 4 096 words 74 times over (the corpus repeats each 73 times, the checksum reads every one back); the vocabulary is built once now and Bun drops 49.8 → 37.6 ms. `tree_eval` and `closures` were rescaled because the 16-byte box made them fast enough that setup was diluting them.

**Read a delta from a back-to-back pair, not from this table against the last one.** The box figures were measured 40 runs each, one build after the other: `tree_eval` 35.2 → 18.8 ms at the old scale, `closures` 31.1 → 13.5, `binary_trees` 6.2 → 4.6, `selfcompile_c` 4 559 → 4 365. `arr_push` read 1.1 ms slower in that pair and 0.6 ms FASTER here — it has spanned 13.6 to 15.5 ms across captures of one unchanged build, so treat it as a layout-noisy row rather than as a cost of the box.


**Forty runs, not twenty, and that is what the short rows needed.** Three 20-run captures of the same build put Go's `string_builder` at 4.2, 4.9 and 6.5 ms — a 55 % spread on a row nothing had touched. The 40-run floor lands at 5.3. Two other 20-run captures were discarded the same way: one read `arr_push` 15.4 ms with `interp` and `ackermann` ~10 % high, and re-measuring those two alone returned them to baseline, so the whole machine had been 2-4 % slow on all four languages that run. The rule applied here, stated so it is not cherry-picking after the fact: **a capture whose sub-10 ms rows disagree with other captures of the same build is discarded as contended, and the published one is the longest run, not the most flattering.**

Reading the table :

- **`mandelbrot`** — Vader native (16.3 ms) beats Go (18.8 ms) and Bun-TS (25.7 ms). After the for-over-integer-range counter-loop lowering (commit `1e268fd3`), the float kernel hits a state where clang `-O3` is doing essentially the same work as `gc`, with a marginal lead from FMA-free arithmetic on this specific kernel.
- **`primes`** — Vader native (25.3 ms) and Go (26.0 ms) run neck-and-neck, both well ahead of Bun (42.2 ms). Trial division is mostly integer modulo, which both AOT compilers turn into the same `udiv` / `msub` sequence ; the sub-millisecond gap (whichever way it tips run to run) is startup noise, and Bun's JIT pays an extra dispatch.
- **`iter_chain`** — Vader native (1.8 ms) beats Go's direct loop (2.8 ms) and crushes the unfused generators — Bun-TS (~37 ms) and Java's Stream API (~40 ms) — by ~25 ×. The lowerer detects `for x in (0..<N).filter(is_even).map(square_i64) { … }` — fluent UFCS chain or struct-lit chain, both bottom out at a `RangeExpr` — and collapses the three-level lazy chain into a single counter loop with the `pred` / `f` calls DEVIRTUALIZED to direct calls, so it stays off the 7-23 × slower unfused path (one `Yielded(T)` heap box + one vtable dispatch per layer per iteration). REGRESSION + FIX (2026-07-16): the `map`/`filter` → `@generator` rewrite (`f2c0fb49f`, bisected) kept the loop fusion but bound the callbacks to fn-value locals called INDIRECTLY through the erased `vader_fn_t` (per-iteration arg boxing + a fn-pointer hop), doubling this to ~4.6 ms. The `devirtualize_fn_refs` lower pass (commit `f231b169b`) restores direct calls — `let f = square_i64 ; … f(x)` and `let f = <lambda> ; … f(x)` are rewritten to call the concrete fn directly — bringing it back to its pre-regression, Go-beating ~2 ms position.
- **`binary_trees`** — Vader native (4.6 ms) leads Go (6.0 ms), both ~3.0 × faster than Bun-TS (13.7 ms). The 16-byte box took it from 6.2, since a `Node | null` field travels boxed. After the nullable-ref inline representation landed, `Node` dropped from 72 B → 40 B (-44 %) and GC pressure dropped accordingly, putting Vader alongside `gc`'s tracing collector on this allocation-heavy workload. Which of the two carries the ★ has flipped between captures (Go led 6.2 to 6.5 on the 2026-09-13 one) — the gap is under 1 ms on a 6 ms sample, inside the ±1 ms scheduling noise this file documents, so read the row as a tie and not as a lead either way.
- **`string_builder`** — Go (4.4 ms) leads, then Vader native (7.3 ms) — ahead of Bun-TS (10.5 ms) after the `StringBuilder` 0/1-part `to_string` fast path landed — with Java (40.6 ms) trailing. The Vader `StringBuilder` stores fragment refs in a `string[]` and flushes once via the `Display::to_string` intrinsic — no per-iter copy — but Go's `strings.Builder` writes straight into a `[]byte` and amortises the grow over a single buffer, which still beats the array-of-refs approach when the fragments are short and many. The remaining gap is two final-pass copies and the GC tracing cost of the ref array.
- **`map_iter`** — Vader native (2.6 ms) leads Go (8.3 ms) by ~3.2 ×, and crushes Bun-TS (35.9 ms) and Java (45.6 ms). Earlier baselines had Vader behind Go (~23 ms, ~2.8 × slower) ; GC + dispatch optims (`O(log N)` string-mark, midir vtable pruning, lower-pass O(1) symbol lookups) first erased the gap, then the compact-dict `MutableMap` rewrite (2026-06) roughly halved it again (6.5 → 3.6 ms). Go's `for k, v := range m` allocates nothing per visit ; Vader's `for entry in m` desugars via `Into(Iterator(Entry(K, V)))` (cf. `std/collections.vader`). The `Yield(Entry)` wrapper folds into a 0-byte tag at runtime (`VADER_TYPE_KIND_INLINE_REF`) and the `Yield(T) | null` return slot folds to a raw `void*` via B1, so the dispatch is alloc-free and pointer-sized. Bun's `Map[Symbol.iterator]` and Java's `entrySet()` both box per visit.
- **`java`** — most Java rows sit at ~39-95 ms (heavier workloads like `arr_rw`, ~94 ms, add real compute on top). That floor is JVM startup + class loading + cold JIT — measurable but bounded now that we precompile in the build phase (down from ~230 ms when each invocation also parsed the source). For steady-state Java throughput (long-running JVM, warmed JIT, millions of iterations) Java would catch up to Go ; we're benching cold script invocations on purpose because that's what `java <Class>` looks like in practice.
- **`arr_rw` / `arr_push` / `str_concat` / `interp`** (Target-ABI workloads, added after the original six) — the Target-ABI paths, now mostly closed. `arr_rw` 59.5 ms vs Go 37.6 (1.6 ×, was 3.2 ×), `arr_push` 13.6 vs Go 31.5 (2.3 × the other way, was 2.0 × behind), `str_concat` 8.3 vs Bun 9.2 / Go 11.7 (the fastest of the four), `interp` 30.1 vs Go 20.1 (1.5 ×) — Vader now edges out Bun (45.7) on `interp` (the workload gained an emoji + codepoint-count checksum, so it is not comparable to the pre-2026-07 `interp` numbers). They exercise the open-coded array load/store, the push/grow + young-arena GC churn, and the off-runtime Buffer-backed string `+` concat / `${}` interpolation paths. **`arr_rw`** dropped from a midir intra-block array-load-forward pass (drops the redundant re-read in `a[i] = a[i] + 1`, commit `6fc1def1`) plus a native c_emit resolve-CSE that shares the buf-forward walk across accesses in one straight-line region (`0af7deb9`). **`interp`** dropped earlier because a `${int}` now writes its digits straight into one exact-sized byte buffer instead of minting a throwaway interned string per part (`2e294f5c`). **`str_concat`** went 21.5 → 8.2 ms on 2026-09-13, a 2.6 ×, and took the row: it had been the one workload of the sixteen where Bun beat Vader. Three lowering changes, in the order they compound. A `+` chain's adjacent literal leaves now merge before the arity is chosen, so an all-literal chain emits no call at all and a mixed one loses the arity its literal runs cost. Consecutive `s = s + …` appends then fuse into a single `concat_N` — building a string in k steps used to cost k buffers and k interns, and the intermediate results were all discarded. Finally `concat_N` calls the `Buffer` impl members directly rather than `new_byte_buffer` / `finish_buffer`, two one-line free wrappers that each pushed and popped a GC shadow-stack frame `cc` cannot elide (the collector reads `vader_gc_top`). The fusion carries the row — 2.3 × of the 2.6 × — and the wrapper change adds 3.4 %. The one measured lever left on this path is the `memset` in `vader_buffer_new`, worth ~4 %: `concat_N` overwrites every byte it allocates, but `BufferAlloc.new_buffer` is a public API whose caller may read a byte it never wrote, so eliding it safely needs a second, uninitialised allocation reachable only from the paths that provably fill everything. **`arr_push`** went 49.3 → 13.6 ms on 2026-09-14 and took the row from Go (31.5), which it now leads by 2.3 ×. (It has read anywhere from 13.6 to 15.5 ms across captures of one unchanged build — its loop pushes `i32` into a PACKED array and never touches a box, so it moves with the runtime's code layout rather than with anything semantic. `-falign-functions=64` is in the tree to damp exactly that.) It had been the workload where the two-level `vader_array_t → vader_array_buf_t` representation cost the most: a push reloaded the header, the buffer pointer, the length and the capacity every iteration, because nothing tells `cc` the call cannot move them. Go's slice is a value in registers ; ours is two indirections. A loop whose only use of an array is pushing to it can hold that state in four locals and commit `length` at the exit — 18 instructions, 6 loads and 3 stores per push become 6, 0 and 1. The analysis is a LOWER pass (`vader/lower/push_cache.vader`), not a backend one: it marks `LoweredArrayPush.cached` where the lift is sound and the marker rides through midir and the bytecode as `ArrayPush.cache_slot`, so a second backend inherits the proof instead of re-deriving it. The emitter re-checks it against the op stream it actually ships, which is the half that matters — midir and the bytecode passes have their say after the proof, and a module const materialised into the slot inside the loop is visible only there. First cut is narrow: packed element kinds only, one array per loop, no nested loops. Before that it had dropped 66 → 49 ms once `push` on a statically-primitive array stopped boxing + calling the generic runtime append and started emitting a typed `vader_array_push_<kind>` inline (typed store at the tail, no box / kind dispatch / write barrier) — one helper per primitive width, full parity with the indexed-store path. It still keeps the `-falign-functions=64` cache-line fix (commit `7a96cc48`) that undid a layout-only regression.
- **`arr_set`** — the same read-modify-write as `arr_rw`, but bounded by `for i in 0..<a.len()` instead of a separate `n`. That lets the lowerer prove `i ∈ [0, len(a))` and — since the body neither allocates nor rebinds `a` — HOIST a's buffer-forward resolve (`while (buf->forward)`) out of the loop into the preheader (BCE resolve-hoist, `vader/lower/lower_for_in.vader`). The per-iteration resolve was a vectorisation barrier — clang couldn't prove `a->buf` loop-invariant — so hoisting it drops the loop from 59.5 ms (`arr_rw`, un-hoisted) to **9.8 ms, 3.8 × faster than Go** (which keeps its own per-access slice bounds checks). Vader's bounds checks *stay* (measured near-free once the resolve is hoisted, and they still catch any residual OOB) ; the whole win is the resolve hoist. `arr_rw`'s `for i in 0..<n` form doesn't qualify — `n` is a separate constant there, and proving `n == a.len()` would need value-range analysis (deferred). A bound that merely NAMES the length does qualify since 2026-09-13: `n :: a.len()` before the loop is carried to it by `bh_pair` as long as nothing between them can change the length (`tests/snippets/bce_named_bound`). Worth ~3.6 × on that shape, which no workload here has. A body that allocates or rebinds `a` (a GC could move the buffer) disables the hoist.
- **`arr_map`** — Σ `square(a[i])` driven through **each language's idiomatic map abstraction**, not a hand loop: Vader's fused `for x in a.map(square)`, JS's eager `a.map(x => x * x).reduce(…)`, Java's `Arrays.stream(a).mapToLong(…).sum()`, Go's `iter.Seq` range-over-func (1.23+). The Vader lowerer fuses `a.map(f)` into a plain `a[i]` counter loop calling the callback (no per-element `Yield` box — fused *array* iterators are alloc-free, unlike opaque ones), and a post-inline **interprocedural purity** pass (`vader/lower/bce_hoist.vader`) proves `square` allocates nothing / suspends nowhere / calls only other pure fns, so the same BCE resolve-hoist fires as in `arr_set`. Vader native (**19.2 ms**) is the *fastest* by a wide margin — **4.7 × Go** (90.0 ms ; its range-over-func inlines well but keeps per-access bounds checks and doesn't vectorise the dependent sum), **7.6 × Java** (146.2 ms, JIT'd Stream), **27 × Bun** (525.1 ms — the eager `.map()` allocates a 1024-elt array every pass) : Vader's is the only map that fully fuses to zero cost. The purity check is **combinator-agnostic** — it names neither `map` nor `filter`, so any pure callback qualifies (the loop is safe iff the inlined body hits no GC safepoint) ; an *allocating* callback keeps its per-iteration resolve + bounds check (no hoist, still sound). 3 × `arr_set`'s pass count so the fused Vader path clears the ~5 ms noise floor and stays regression-gated.
- **`hashmap`** — Vader native (29.3 ms) is the *fastest*, ahead of Go's built-in `map` (44.8 ms) and ~4.1 × faster than Bun (120.7 ms) — a touch quicker since the compact-dict's `i32`/`usize` key + value `push` went typed. The compact-dict `MutableMap` (open-addressed `i32` index over dense entry arrays, cf. `map_iter`'s note) absorbs the insert / lookup / delete / grow churn with no per-op allocation ; this is the build-and-probe counterpart to `map_iter`'s pure iteration, and the shape a compiler's symbol table / interner actually sees. All four maps grow from empty — no port pre-sizes — so the row measures the rehash / grow path it advertises, not just steady-state probing. Keys are `(i·STRIDE) mod KEYSPACE` with STRIDE coprime to the prime KEYSPACE, so all 100 000 keys are distinct and the set is identical across ports.
- **`ackermann`** — pure non-tail recursion, zero allocation, isolating the raw call path (prologue / epilogue, argument passing, direct-call dispatch) the way `binary_trees` (allocation-dominated) can't. Vader native (40.7 ms) lands level with Go (43.9 ms) and Bun (46.8 ms), ahead of Java's JVM-startup floor (58.6 ms). At this size a large share of the wall-clock is process startup (Vader's is ~0), so like `iter_chain` this row stays startup-sensitive ; the *pure* per-call overhead only separates the field at far larger n — `A(3,11)` is ~10 × the calls, and there Vader native is the **slowest** (a real gap), but that would blow the suite's tens-of-ms budget, so we size down to `A(3,9)`.
- **`wordcount`** — byte-scan / tokenize, the inverse of the string-*building* rows. Vader native (10.1 ms) is the *fastest*, **2.7 × Go** (27.3 ms) with its `[]byte` range loop, and well ahead of Bun (45.4 ms) and Java (60.5 ms). It was 39.5 ms before the dominance resolve-CSE (2026-07-28) and 25.5 ms just after. The rest of the drop happened between that capture and the 2026-09-13 one, and this file did not track `bench/baseline.json` across the 2026-08-30 rebaseline in between — so no single landing is claimed for it here. The workload itself has not moved since 2026-07-19, so the figures are comparable. Note that its `nb :: data.len()` sits OUTSIDE the `PASSES` loop, which is why the named-bound resolve-hoist (see `arr_set`) does not fire here — measured at −1 %, i.e. nothing. The scan loop is `no_frame`, and its whitespace state machine branches on every byte, so under the old rule each `If` dropped the cache and the very next `u8[]` load re-resolved the buffer ; the resolve now survives into the branch arms. Vader scans the zero-copy `bytes()` view through the open-coded `u8[]` load — the lexer's inner loop, which nothing else in the corpus measures. What's left of the gap is the branch-heavy state machine, not the load (per the u8-read note, `cc -O3` already erases the per-byte tax).
- **`quicksort`** — array get/set + swaps + bounded recursion, the *same* hand-written median-of-three Lomuto sort in every language (not the stdlib), so it compares codegen rather than library quality. Go (37.3 ms) leads by a nose, Vader native (40.0 ms) is a close second — ahead of Bun (74.9 ms) and Java (84.0 ms). **Was 49.2 ms (1.4 × Go) until the dominance resolve-CSE landed (2026-07-28), a 23 % drop.** The partition loop is a `no_frame` fn — provably no-alloc, so no GC safepoint can move a buffer anywhere in its body — which now lets a resolved buffer survive *entering* a nested scope (`Block`/`Loop`/`If`) instead of being dropped at every control-flow op (`invalidate_resolve_cache`, `vader/c_emit/walker.vader`). The partition's compare/swap arms each re-resolved the same array before ; they now share one resolve per iteration. Exercises the swap / reassign lowering (a former miscompile site) and the typed `a[i]` store ; the input is a coprime-stride permutation of [0, N) so the sorted result is exactly [0, N) and the order-sensitive rolling-hash checksum proves the sort ran. Recursing the smaller half bounds the stack to O(log N).
- **`wordfreq`** — Go (11.1 ms) leads, Vader (22.2 ms) is 2.0 × behind, ahead of Bun (37.6 ms) and Java (57.3 ms). Slicing a token out of a byte corpus makes a *fresh* string, and in Vader a string IS an atom (`vader_string_t` is a `u32`), so `bytes_to_string()` has to hash the bytes and probe the global atom table before the map ever sees the key. Cutting the workload in three says where the time goes: corpus build + slice alone is **6.7 ms**, adding `bytes_to_string()` takes it to **15.8 ms**, and adding the map takes it to **22.2 ms** — so the interning step costs **9.1 ms** and the map step **6.4 ms**. **The gap is the interning, which Go does not have at all**: a Go string is a pointer and a length. It is a deliberate trade — that one hash is what makes `==` a single integer compare everywhere else in the language, and it dedupes 98.6 % of the 300 000 slices down to 4 096 atoms. The vocabulary is rendered once and both the corpus and the checksum read it back; rendering on demand did the base-26 division 74 times per distinct word, which was over half the Bun-TS column and none of what the row is named for.
- **`shapes`** — Vader (22.7 ms) is the *fastest*, ahead of Go (31.4 ms), ~2.0 × Bun (44.3 ms), with Java (76.9 ms) trailing. This is the counterpart to `iter_chain`: there the lowerer proves the callee and the call disappears, here it cannot and the call has to happen. Vader's trait dispatch is **not a function-pointer vtable** — emit generates one dispatcher per trait method that switches on the receiver's box tag (`vader_vt_Shape__area`, a `switch (recv.tag)` over the three impls), which `cc` compiles to a dense jump the predictor handles well; Go's is an indirect call through the itab. That is why the row tips this way, and it is also what the row does *not* prove: a switch is O(impl count) where an itab call is O(1), so a trait with many impls would narrow or reverse it. Three impls, cycled so no two consecutive elements share a receiver type, is what is pinned here — a monomorphic inline cache would miss on every third element, which is the point.
- **`tree_eval`** — Vader (41.5 ms) is the *fastest*, ahead of Go (53.5 ms), and well past Bun (121.9 ms) and Java (107.7 ms). It was 1.4 × BEHIND Go until `vader_box_t` went from 24 bytes to 16: the walk passes a box per recursive call, and at 24 bytes that was three loads, three stores and a pointer setup where Go's 16-byte interface is two register moves. The row is what found that, and the disassembly of `main_evaluate` is what said it — two earlier hypotheses died first, including hand-patching the emitted `if` chain into a real `switch`, which moved nothing. A four-variant `match` over a closed union, on a tree built once and walked forty times, so the allocation amortises out and what remains is the tag dispatch plus the recursion. `binary_trees` conflates the two — its walk is a single pass over what it just allocated, and its match has two cases — and `selfcompile_c` runs this shape constantly but only reports it as a 4.5-second aggregate that cannot localise a regression. This is the compiler's own inner loop, and the row exists so a change to how a union carries its tag, how `match` lowers a four-way dispatch, or how each arm gets its field offsets has somewhere cheap to show up. Every operation is additive, so the value stays exact in an f64 mantissa and the four ports agree on the checksum bit for bit.
- **`matmul`** — Go (14.1 ms) leads and Vader (29.9 ms) is 2.1 × behind, ahead of Bun (41.3 ms) and Java (48.2 ms). A second dimension is not more of the first: a row is its OWN `vader_array_t`, so `right[k][column]` walks two headers and two buffers where a 1-D access walks one, and the inner loop does that on every iteration. `left_row` is hoisted by hand in all four ports so the row measures the indexing rather than the loop shape. Go's `[][]int64` pays one indirection too — its rows are slices, not a flat block — so the gap is ours to explain and this row is where it will show up.
- **`closures`** — Go (22.3 ms) leads Vader (36.1 ms) by 1.6 ×, with Bun at 44.0 ms and Java at 48.2 ms. It was **3.5 ×** behind and behind Bun too until the box shrank to 16 bytes — a closure's captured value travels boxed, so this row moved for the same reason `tree_eval` did. Two costs are stacked on purpose. A capture that is MUTATED forces the local into a heap cell, so `counter = counter + 1` under a lambda becomes a load, an add and a store through a pointer where outside one it is a register. Then 500 closures are called round-robin, each with its own environment, which keeps the call site megamorphic and mints one allocation per closure. `iter_chain` and `arr_map` both exist to show the lowerer DELETING this indirection, and `devirtualize_fn_refs` removes it wherever the callee is statically known — this row is what is left when it cannot be.
- **`fmt_float`** — Go (5.8 ms) leads by **1.7 ×** over Vader (9.6 ms), with Bun (12.6 ms) now behind and Java at 49.2 ms. It read 40.4 ms and was the widest gap in the corpus until 2026-09-14. `interp` covers integer formatting, which writes its digits straight into a byte buffer; a float goes through Ryū (`lib/std/core/dtoa.vader`), several hundred lines of pure Vader that no benchmark had ever exercised. Two files this note used to name alongside it are NOT on the measured path: `f2s.vader` is the f32 formatter, and `bigint.vader` runs under `@comptime` to build the power-of-5 tables — at runtime it serves only `parse_float`. A profile put the cost nowhere near that arithmetic: the whole Ryū core, `mul_shift_all_64` included, was **3 %** of the row, while interning, the array pushes, the concatenations and the atom table's `memcmp` / `memcpy` — all of them the presentation layer turning digits into a string — came to **68 %**, before counting its share of `vader_gc_alloc`. `digits_of` minted a `string[]` of one-char interned atoms and `join_range` then concatenated them one at a time, so a 17-digit rendering cost two growable arrays and one atom intern per digit — each of those interns hashing a prefix that was thrown away one concatenation later. It now writes into a single right-sized `Buffer` and interns once, the shape `format_unsigned` has used since the Target-ABI work: **40.4 → 9.6 ms, a 4.2 ×**, byte-for-byte identical to the old code over 408 055 renderings across all four `Number::toString` branches, with no `vm.snapshot` in the corpus moving. What is left is the string model, not the formatter: holding the rendered length fixed and dropping only the final `intern_string` takes 600 k values from 91.0 to 31.1 ms, so **two thirds of the remainder is turning 17 bytes into an interned atom** — FNV-1a-64 over the content, a probe, a `malloc` and a `memcpy`, for a string this workload never compares to anything. Go's `strconv` hands back a `(ptr, len)`. That is the price of `==` being an integer compare everywhere else, and the same tax `wordfreq` and `split_join` pay. The one Vader-side item left is elsewhere again: `umul128` and `mul_shift_all_64` return tuples, and a tuple return is a heap object — three GC allocations per formatted float, against the one the `Buffer` costs, for values the call site destructures on the very next line and never lets escape. Multiples of the divisor are skipped because Vader and Java print `1.0` for an integral value where Go and JS print `1` — a difference of convention, not of work, and the four ports agree byte for byte on everything else (verified, not assumed). Values stay inside [1e-3, 1e5) so no port switches to exponential notation; Java crosses over at 1e7, which makes the window Java's.
- **`async_await`** (two columns) — Vader (33.2 ms) is 2.2 × faster than Bun (74.0 ms). Every await is on an already-settled value, so nothing parks on a scheduler and nothing waits on a timer: what is measured is the block-split lowering and the frame that carries locals across a suspension point. **Go and Java are deliberately absent.** Go has no async/await, and its nearest idiom — a goroutine and a channel round-trip — parks on the scheduler, which is a different and far heavier thing; Java is the same story with virtual threads. Those rows would report which concurrency model is cheaper rather than whether our coroutine lowering regressed, which is not what this corpus is for. The harness drops an implementation whose source file is absent, so the two columns are simply empty.

- **`parse_float`** — Go and Bun are level at 24.5 and 23.8 ms, Vader (32.8 ms) is 1.3 × behind, and Java trails at 89.3 ms. Read this row NEXT TO `fmt_float`: they are the two directions of one subsystem, both pure Vader. Decimal → f64 is 1.3 × off; f64 → decimal was 6.9 × off and is 1.7 × now. The pair did its job — it said the cost was on the rendering side and not in float handling generally, which no single row could have said. What it could not say is WHICH half, and this file guessed Ryū and the big-integer kernel under it; a profile then put the Ryū core at 3 % and the big-integer kernel nowhere at all, because it does not run on this path — the digits-to-string layer sitting after Ryū was over 80 %. A pair of rows narrows the search, a profile ends it. `parse_float` also used to be `strtod` natively and a naive accumulator on the VM, and the two disagreed on real inputs — one implementation now serves both, so nothing but this row will notice if it regresses. The checksum sums the two halves of each result's bit pattern, which is what correct rounding means and what a value-level sum would blur.
- **`sort_by`** — Vader (31.5 ms) is the *fastest*, **2.1 × Go** (65.0 ms), 2.5 × Bun (78.5 ms), with Java at 147.2 ms. Distinct from `quicksort`, which hand-writes a monomorphic partition and compares codegen: this one calls `std/sort`'s merge sort through a fn value, so it measures the library plus one indirect call per comparison — the shape `sort(items, by_name)` actually takes. `devirtualize_fn_refs` turns that fn value into a direct call, which is most of the lead. Go's `slices.SortStableFunc` and Java's TimSort both keep the indirection; Java additionally boxes, since `Arrays.sort(long[])` takes no comparator. The comparator orders on a derived key so equal keys are common, and the checksum reads their order back — which is why every port uses its STABLE sort.
- **`split_join`** — Go (9.4 ms) leads by **3.6 ×** over Vader (33.6 ms), with Bun at 18.2 ms and Java at 63.8 ms. The gap is representational, and it is the same one `wordfreq` measures from the other side: `strings.Split` hands back slices that SHARE the original string's bytes, so Go allocates nothing per field and copies nothing, while a Vader part is a fresh interned atom — hashed, probed, and stored. That buys `==` at one integer compare everywhere else in the language, and this is a row where the bill arrives. None of the other string workloads cut a string into an array: `str_concat` grows one string, `string_builder` appends fragments, `wordcount` scans bytes without producing any, `wordfreq` slices at computed offsets.

- **`selfcompile_c`** (Vader-only, compile-time) — times the compiler emitting C for the whole compiler. **4.33 s, roughly half the 8.7 s of an earlier baseline** : the 2026-07-16 fix that stopped the single-expression inliner from splicing statement-bearing trait-method bodies (e.g. an enum's `= match self { … }`) removed a pathological inline explosion in the compiler's own code — one diagnostic snippet's bytecode collapsed 13818 → 129 lines — so there is far less C to emit ; the `devirtualize_fn_refs` pass shaves a little more.

The `mandelbrot` checksum splits three ways : Bun-TS / Java agree at 5 705 453, Vader-native lands at 5 705 449 (a 4-iteration drift, ~7 boundary pixels where clang's reassociation under `-O3` reorders a `z² + c` term and flips the escape test one iteration earlier), and Go lands at 5 689 008 because `gc` fuses `a*b + c` into a single FMA instruction with one rounding step on arm64. All three are mathematically correct ; only the rounding model differs.

## Adding a workload

1. Write the kernel in `bench/<name>/<name>.vader`. Print a one-line checksum to stdout.
2. Port it to `bench/<name>/<name>.ts`, `bench/<name>/<name>.go`, `bench/<name>/<name>.java` — all colocated in the same directory. Keep the algorithm bit-identical (the harness verifies checksum equality against the committed baseline). A port may be omitted : the harness silently drops any implementation whose source file is absent, so a Vader-only workload still works (its row just shows only the `vader-native` column).
3. Add an entry to `WORKLOADS` in `bench/run.ts`.
4. Add the Vader binary line `bench/<name>/<name>` to `.gitignore` ; the `.c`, Go binary and `.class` artefacts are already covered by the `bench/*/*.c`, `bench/*/*_go`, `bench/*/*.class` globs.
5. Run `bun run bench -- --update` to extend the baseline (baselines are machine-specific — a new workload simply isn't regression-gated until someone records it on the canonical machine).

## Caveats

- The natively-compiled Vader path uses `--release`, which sets `-O3 -DNDEBUG` and post-link `strip`. Compiler is the system `cc` (clang on macOS, gcc on Linux).
- Bun's measurement of process wall-clock includes its own startup — measured at 11.4 ms on macOS with an empty script. On a workload that takes 15 ms total that is two thirds of the run, so read every `bun-ts` row under ~15 ms (`str_concat` 9.2, `string_builder` 10.5) as mostly startup rather than as a measurement of the language's throughput. The same caveat applies to Java, at a much larger floor — see its bullet above.
- The VM-path numbers measure `./build/vader run …` end-to-end, including the Vader parse + typecheck + lower + bytecode pipeline. They'll drop substantially once the bytecode-on-disk cache lands (TODO §3.5).
