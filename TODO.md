- [ ] **`T[]` should satisfy a `[C: Index]` / `[C: IndexSet]` bound: DEFERRED, a dynamic-dispatch feature, not a perf one** (revisited 2026-07-20). Direct `arr[i]` / `arr[i] = v` lower to the built-in fast op (concrete `ArrayGet`/`ArraySet`, 0 alloc) and STAY that way regardless of this item: nothing here touches the array fast path. The only thing an array-`Index` impl adds is letting an array satisfy a **generic** `[C: Index]` bound; since generics are erased (.NET model), that path is *inherently* a runtime vtable dispatch (slow, rare), not something the fast array machinery can be "moved into". Prereq **(1), SHIPPED** (`272af6472`, snippet `generic_index_dispatch`): the index OPERATOR `c[0]` / `c[0] = v` now dispatches through a `TypeParam` `Index`/`IndexSet` bound for user **struct** implementors (`infer_index` / `check_assign` record the bound's member; `lower_index` / `lower_assign` emit a vcall on an erased instance). Remaining blockers, both on the **erased array receiver** (found 2026-07-20, `@intrinsic T[] implements Index/IndexSet` attempted + fully reverted): **(a) vtable key**, a concrete `i32[]` carries its element-specific type id (header `type_index`, e.g. 2) but the single materialised row is keyed on the erased `Any[]` (e.g. 8), so both the VM (`receiver_type_id_of` → `a.type_id`) and native (`switch(recv.tag)`) miss; **(b) erased primitive read/write**: the erased body emits `array.get <ref>`, whose native path (`vader_array_ref_load_box`) only handles `element_kind ∈ {REF, BOXED}`, NOT a primitive-packed buffer (`i32[]` = 4-byte slots) → would read a 24-byte box from a 4-byte slot (the VM escapes via uniform boxing). Two design options if ever needed: **A. full erasure**: extend the runtime ref-load/store helpers to box/unbox primitive elements via `element_kind` + `element_tag`, and expand the one erased row over every array type in the table (generalises to any `T[] implements Trait` virtual dispatch); **B. per-element monomorphisation**: materialise concrete `at__<elem>` / `set_at__<elem>` keyed on the concrete array type (fast reads, no runtime change, more plumbing to track which element types reach the bound). Defer until there's a real caller passing an array to a `[C: Index]` generic.

- [ ] **A tuple crossing a call boundary is a heap object: measured 2026-09-21, and the answer is `for c in s`, not `dtoa`.** A `fn(...) -> [A, B]` allocates in the callee and returns `void*`; a `fn(p: [A, B])` makes the CALLER allocate. Either way the object is destructured on the receiving line and never retained.

  **What it costs: 3-5 ns per crossing**, measured three independent ways (a returned pair, a parameter pair, and the `utf8_decode_len` path, since replaced by `codepoint_at_byte`) and stable. GC pressure adds nothing on top: the collector is a copying Cheney, so an ephemeral tuple is never a survivor and is never traced.

  **Where it does NOT matter, both checked rather than assumed:**
  - `for [k, v] in m`: already stack-promoted. `escape.vader` sees the tuple built and destructured in one fn and emits a single `_storage` slot reused every iteration, zero `vader_gc_alloc`. The big producer is already free.
  - `dtoa` / `fmt_float`: inlining `umul128` by hand takes `f2s` from 3 allocations per float to 1, for **2.4 % against ±5 % of noise**. Not detectable. Same checksum (`425079331`), verified.
  - The compiler itself: only 12 fns in the whole tree return a tuple, none on a hot pass. The lexer, a hot pass, walks its source with `codepoint_at_byte`, which returns a pair: the C compiler keeps it in registers once inlined, and self-compilation did not move when it replaced `char_at_byte` (2026-10-14).

  **Where it does matter: `for c in s`, the plain way to walk a string.** 26.8 M codepoints, three shapes of the same loop:

  | | time | per codepoint |
  |---|---|---|
  | `for c in s` | 316 ms | |
  | manual loop calling `utf8_decode_len` (since replaced by `codepoint_at_byte`; tuple, no iterator) | 177 ms | tuple = **3.1 ns, 26 % of the run** |
  | manual loop, no tuple and no iterator | 95 ms | iterator = 5.1 ns, 44 % |

  So the idiom costs **3.3×** its hand-written equivalent, and the tuple is a quarter of that. **The iterator machinery is the bigger half**: whoever picks this up should take that first; the tuple is the second lever, not the first.

  **The shape to emit, if it is taken.** Out-params (`f(inA, inB, &outA, &outB)`) beat returning a flat struct by value on 8-byte tuples (16.4 ms vs 18.8 ms, because two `i32` packed in one register have to be unpacked) and tie past 16 bytes, where the C compiler inserts the same hidden pointer itself. Out-params are also uniform: no ABI threshold to track, no flat struct type to declare beside the GC one.

  **Where it belongs: midir, not `c_emit`.** The pattern is already visible there on both sides, the callee's `struct_new` has `return` as its only use, and every use of the caller's `call` is a `field_get`. That is the analysis `escape.vader` already performs, and doing it there means the VM benefits too instead of diverging from native.

  **The risk that decides whether it is worth it.** With `&outA`, the caller takes the address of a local; if the tuple carries a ref field (`[i32, string]`), that local must be a shadow-stack root BEFORE the call, initialised, or the collector scans an indeterminate slot. Today one root (the tuple pointer) covers it. A first cut restricted to all-primitive tuples sidesteps this entirely and still covers `codepoint_at_byte`.

- [ ] **Allocation-use analysis → stack-alloc / interning / value-structs** (escape analysis, broadened 2026-06-20). One whole-program dataflow over midir (`vader/midir/`) computes, per allocation site / per type, *how the value is used*: does it **escape** its creating fn (return / store-to-heap / capture), is it **mutated** after construction (a `struct.set` scan, the lowered IR makes this a direct walk), is it **compared by reference identity**. Those facts feed THREE complementary GC-pressure optimisations, each attacking a different slice of the self-compile memory profile (the two halves measured by `bun run bench:profile`: ~986 MB GC-copied / 32 cycles of **churn** + ~512 MB **retained** live-set, ARRAY_BUF/`MutableMap`-dominated):
  - **Stack-allocation**: allocations that provably don't escape go on the stack (or are freed eagerly) instead of the Cheney arena. Attacks the **churn** half (short-lived CFG-node / temp traffic). Caveat: a stack slot must not be a GC root the moving collector tries to relocate.
  - **Interning (hash-consing)**: immutable, duplicated, long-lived values are deduplicated to one shared instance. Attacks the **retained** half (Type IR, `Symbol`, `BcType`, `MutableMap` entries held across passes), note this is the INVERSE class to stack-alloc: the escaping, long-lived values stack-alloc can't touch are exactly interning's target. **Vader soundness condition**: `==` on a struct without an `Equals` impl is *reference identity* (SPEC §"Memory Model"), so interning is sound only for a type that is immutable AND never identity-compared (has `Equals`, or is never `==`-ed, e.g. `PrimitiveType`, compared via `equals_type`/`canonical_key`, qualifies). Proving "never identity-compared" automatically must bail in erased generic/union contexts, so the realistic form is an opt-in **`@intern` decorator the compiler *verifies*** (immutability + Equals/no-identity-compare → error if violated) then generates the content-keyed construction: the Rust `Ty` / LLVM type-uniquing / GHC model (always annotated, never auto-derived, for exactly this reason). Profitability caveat: intern only bounded-value-set types (few distinct values), else the intern table itself retains everything → a leak.
  - **Value-type structs**: small immutable never-trait-boxed structs passed by register instead of heap-boxed. Shares the same immutability fact; see the §3.5 "Value-type structs" item for its open trade-offs (`@value` vs auto-detect, `is Trait` interaction, multi-register ABI).
  The first concrete interning win: `mk_primitive` singletons (`vader/core/types/types.vader`, 17 primitive names incl. `null`): is a safe MANUAL instance (never `==`-compared, 17 bounded values); doing it generically is this chantier. **When generic `@intern` lands, REVERT that manual interning**: replace the hand-rolled `mk_primitive` singleton table with `@intern` on `PrimitiveType`, so there's one mechanism, the manual table would otherwise duplicate (and could conflict with) the generic pass's content-keyed construction. Architecture-level → explore-before-commit + review. Related §3.5 items: escape (stack-alloc), value-structs, self-host typecheck working-set.

- [ ] **`match` lowers to independent `if`s, never a `switch`** (noted 2026-08-28, user observation, confirmed on the emitted C). A six-arm `match` over an `enum(u8)` emits:

  ```c
  static vader_string_t mt_name(uint8_t l0) {
      if (l0 == INT32_C(0)) { return 1u; }
      if (l0 == INT32_C(1)) { return 2u; }
      ...
      vader_unreachable("unreachable return in mt$name");
  }
  ```

  `docs/ARCHITECTURE.md` (*Lowered AST*: "There is no decision-tree compilation") documents this as the deliberate lowering, so it is a debt taken knowingly, not an oversight.

  **The nuance that decides what to measure**: because every arm `return`s, these are semantically already an `else if` chain, control never falls through, so the *branch count* is not the cost. What is lost is the DENSITY information. `switch (l0)` over `0..5` tells the C compiler a jump table is legal; a run of comparisons leaves it to prove that, which gcc/clang often do for this exact shape but not always, and never once the values are sparse or the arms carry guards.

  **So the first move is a measurement, not a rewrite.** Compile a dense enum `match` at `-O3` and look for a jump table (`jmp *%rax` / `.rodata` offsets) versus a comparison chain. If the table is already there, this is worth nothing on the C backend and stays a note for the future WASM emitter, where `br_table` has to be chosen explicitly and nothing will infer it. If it is not, the fix is narrow: emit `switch` when every arm is a literal over one integer scrutinee, keep the `if` chain for everything else (type tests, guards, string arms, or-patterns). Cross-ref the bytecode side: the VM dispatches the same shape and has no table either.

  ⚠️ Not to be confused with a correctness matter: the chain is correct today, and `@partial` / T3013 exhaustiveness is unaffected either way.

  **The general form of the same work** is decision-tree compilation (Maranget): sharing tests across arms instead of re-testing the scrutinee per arm. Only worth it if the measurement above shows the chain costs something.

The typer and the lowerer each resolve `a.f(b)` through their **own** ladder, the typer records coercions (`into_coercions`) and the lowerer **re-derives everything** from scratch, so the two can disagree, and every fix has to be applied twice by hand. ⚠️ **A parse-time desugar cannot fix this**: `a.f(b)` has ten distinct resolutions (struct field, trait impl, free fn by UFCS, namespace member, enum variant, intrinsic, …) and the parser knows none of them. **The three defects, all reproduced against `build/vader` at `e86d0cc13`:** **(a)** a free fn **silently shadows a struct field** of the same name: member should win; **(b)** the typer and lowerer disagree and the **IR carries a lying type**; **(c)** the typer accepts what the lowerer **cannot emit** (the panic site the distinct-cast bug, `docs/HISTORY.md` §1.13d, shares). **Staging:** phase 0 free cleanup with no semantics; phase 1 member-before-UFCS precedence (fixes (a)); phase 2 the un-called curried `FieldExpr` (fixes (b) and (c)); **phase 3 is the real chantier, elaboration**: the typer *writes* the resolved dispatch at every site and the lowerer *reads* it instead of re-deriving, landed in three independently shippable steps (3.1 write it while lower still uses its own ladder, guarded by a verifier asserting the two agree; 3.2 switch the shapes that are clean; 3.3 retire the lowerer's ladder shape by shape until the fallback is dead). What elaboration does **not** remove: the typer's own ladder, there will always be exactly one, which is the point. **Re-verified 2026-10-02**: (a) still prints 20 where 42 is expected, (c) still panics, with a message (`method reference on a primitive`) that names the wrong cause; and a fourth case: an overloaded DIRECT call inside a generic body is chosen wrongly per instance (`show("s")` prints `i32 24`). **Settled 2026-10-13 (ADR 0057)**: a call in a generic body is resolved against its type parameters, once, and every instance runs that choice, direct and UFCS calls alike; the lowering no longer searches again for a UFCS call the typecheck settled, and its own free-fn search (`find_free_fn_ufcs`) is gone: array ops yield to a chosen free fn, a call through a field's fn value is never redirected, and a string loop steps std's `chars` by identity. A generic call's type arguments now come from its record (`DirectFn.bindings`, ADR 0056); only a fused generator combinator still unifies them (`gen_combo_subst`, see the call-site record entry below). **Seen 2026-10-20, a variant of (a)**: with a GENERIC free fn `second :: fn<A, B>(a: A, b: B) -> B = b` in scope, `p.second` on any struct, generic or not, is T3018 (`` `fn(B) -> B` does not implement it ``); a non-generic `second(i32, i32)` does not do it. `generic_angle_decl` names its fn `pick_second` because of it.

- [ ] **The call-site record (ADR 0056): what its readers left open** (2026-10-13). The typecheck files what each site invokes (`TypedProgram.call_sites`); the lowering, the LSP's references and rename, the effect summary (ADR 0059) and the propagation of type-parameter observation read it.
  - **What the lowering still chooses itself.** It reads the record for every call, operator, index, conversion, `for` and interpolation (ADR 0056); what remains outside it: an explicit `f<T>()` takes its written type arguments (the typecheck seeds them by looking the callee's type parameters up in the caller module's `idents`, unverified for an imported callee); a fused generator combinator unifies its type arguments against the fused element (`gen_combo_subst`); a structural `==` walks its parts (`value_eq`, the record lists their `equals` flat); `concat_N` reaches the buffer API by name (`find_impl_member_for`); the fast paths the verifier lists (`tests/callee_verify.test.ts`).
  - **LSP.** A trait member has no references: neither its declaration in the trait, nor the calls dispatched through a bound or a trait value, nor an inherited default. The same set is what renaming a trait member with every impl would need; renaming one impl's member is refused today, since its trait fixes the name. A trait's default body has no record of its own (it is checked through its copies), so nothing in it is a reference. Goto-definition on a bare overloaded call lands on the first overload, while references go to the one called. `documentHighlight` matches by name.
  - **Type-parameter observation.** An impl member relays only when its signature past the receiver names a type parameter. A generic struct's impl member would make its callers keep concrete instances for nothing, once the unresolved-callee panic such a member hits at emit today is fixed.
  - **Namesakes.** An impl member's body is checked against the return type of a free fn of the same name (T3083).
  - **Overloads behind a namespace alias.** Only the first declaration is seen: with `describe(x: i32)` declared before `describe(x: string)`, `L.describe("a")` is T3001. A bare imported name picks among its overloads.

- [ ] **W0019 misses the writes it cannot place in order or through an alias** (2026-10-16, ADR 0067). The check asks whether the body reads the name anywhere, not after the write: `x :: c.n; c.n = 2; return x` and `c.n = c.n + 1` are silent where `c.n += 1` warns. A name bound to the copy is a read of it (`d :: c; d.n = 2`, `rows :: TABLE; for r in rows { r.n = 0 }`), and a write through a call (`c.items.push(0)`, `reset(c)`) lends the name, so `for row in TABLE { row.items.push(x) }` is never reported. Silent is the safe side; the order needs liveness on the lowered control flow, and the aliases a binding that took only copies. A write through a user `IndexSet` (`g[0] = 5`) is a call too, and is not reported. The walk returns no slot both for a value nothing shares (a scalar, a fresh literal, a diverging branch) and for one shared without being lent (a lambda's parameter, `await`), so a join of a frozen value with a branch that holds no slot is never warned about (`one_of`), `c :: if f { Cfg {} } else { CFG }` included. Giving the shared values a slot with no root, as a function's parameters have, would leave no slot meaning only "nothing shared", and `one_of` would go.

- [ ] **`@singleton`: what is left after the first cut** (noted 2026-10-16, ADR 0068).
  - **The C accessor pays a GC frame on every call.** The accessor holds the instance in a temporary across the init call, so its body carries a frame even on the ready path, about five times the cost of a frameless read. A fast path that reads the ready instance before any frame exists needs the emitter to leave a call in return position without a frame (shrink-wrapping was a NO-GO elsewhere, so this is a narrower rule).

## Phase 2 (Self-hosting) leftovers

Self-hosting is done: the native compiler re-emits its own C byte-identically
(2026-06-05) and the TypeScript compiler is gone. The port's history lives in
[`docs/HISTORY.md`](./docs/HISTORY.md); what follows is what the port left open.

### Typecheck and lowering

- [ ] **`==` between two kinds no rule covers is accepted** (found 2026-10-26). `pair == "x"` (a tuple against a string), `colour == "x"` and `colour == 0` (an enum against a string or a number) pass `vader check`. The tuple one answers `false` on the VM and its C does not compile; the enum against a string is refused by the VM (`i32.eq may meet ref`) and answers `true` natively; the enum against a number compares the variant's value on both backends (`.Green == 1` is true), though an enum does not widen into an integer (SPEC §Enums). `check_equality` (`vader/front/typecheck/binary.vader`) has a rule per pair of kinds it knows and falls through to `return TY_BOOL` for the rest. A closing rule `if !comparable { T3001 }` would reuse the `comparable` it already computes, but has to leave alone what compares through `Any` or an unresolved type: a design call, not a one-line fix. The free number literal beside a string, a bool or a char is already refused (T3001).

- [ ] **A copy of a `@comptime` table is rebuilt element by element** (found 2026-10-26, `examples/raycaster`). A use of a module constant that needs a copy of its own (returned or stored, or bound to a name that is then written, stored or returned: `vader/front/effects/frozen.vader`) reads a fresh value, and the fresh value of a pooled table comes out of its `__const_<name>` accessor (`const_fresh_wrap`, `vader/lower/inline_consts.vader`), which pushes every element and then `array.new N`: O(N) code once per table, O(N) work at every such read. The raycaster's eleven textures of 21 760 texels, read that way, made a 6 MB C file and a 90 s build; the example now hands them to the drawing functions as arguments, which shares them. The table is already in the read-only pool, so a copy could be one block copy from it. Touches how lowering materialises constants: to review before any code. Under `vader run` the accessor loads in linear time, but its `array.new` is one `Boxed` op, whose pop count `boxed_counts` packs into a 21-bit operand (`vader/vm/reg_code.vader`): a table of 262 144 elements or more stops on "an operand is past the register engine's encoding", as does an array literal of that size anywhere. ### Self-host perf

Measured 2026-10-02 on the self-compile: `MutableMap` operations are ~60 % of the
typecheck pass, and the cause is probe clustering, not the number of lookups:
`idents` lookups average ~480 probe steps (span keys keep `column ^ line` in the
low bits; node-id keys hash to themselves and wrap a growing table). An avalanche
mix in the hash cuts the typecheck pass by ~45 % with the emitted C unchanged; a
flat array in place of a map is worth ≤ 8 % once that lands.

### 3.4 Stdlib expansion
- [ ] **No blocking sleep** (found 2026-10-26). `std/time` measures time but cannot wait: the only `nanosleep` is the async scheduler's (`vader_sched_park` in `runtime/c/vader_runtime.c`), reached through `std/async::sleep`, which returns an `Async<null>`. A program with no async code that has to pause, such as one waiting for a sound to finish, spins on `monotonic()`. A `sleep(d: Duration)` over `nanosleep` / `Sleep` would be one intrinsic per host.
- [ ] **`std/json` v2: generated serialisers, and a plug-and-play way to connect them** (expanded 2026-08-27, user request). Today the surface is `JsonValue` + `parse` + `stringify` / `stringify_pretty`: struct ↔ JSON is hand-written by the caller. The goal is generated `to_json` / `from_json`, and (the part that matters) **a library ships its generator and a project connects it, rather than every project rewriting the generator**.
  - **Already prototyped, by hand**: `tests/fixtures/hook/json_derive/build.vader` walks each struct's field types and emits one serialiser per struct into the struct's own module. It works end to end (the built binary prints the right JSON, string escaping included) but it is **~90 lines of driver code the user writes, per project**: exactly what plug-and-play should remove. Note the natural split it already shows: the *generator* is build-time, the *generated code* calls `std/json` at runtime.
  - ⚠️ **Layering constraint, measured: the stdlib imports nothing from `vader/`.** A generator must read `AST.StructDecl`, i.e. `vader/front/parser`, so `std/json` cannot ship one without the stdlib gaining a dependency on the compiler, and a *companion* module under `std/` would only move that dependency, not remove it. **Resolved in design 2026-08-27, see the `lib/` item in §3.7**: the AST moves to `toolchain/ast`, a compiler-free leaf, and `json` becomes a namespace of its own, so the generator lives in a build-time submodule of the library, depends on `toolchain/ast` rather than on the compiler, and is never in a program's runtime closure, lazy resolution does not descend into subfolders (`front/resolver/lazy.vader:220-232`), so importing `json` never pulls its build-time submodule.
  - **The imperative half needs no new compiler mechanism.** A library can export `derive_to_json :: fn(s: AST.StructDecl) -> string` today, and connecting it is one call: `ctx.emit_module(t.module_name, derive_to_json(s))`. What is missing is a **convention** (an agreed signature and module name) so every library does it the same way and a driver can connect several without bespoke glue.
  - **The declarative half is the new machinery.** "Connect it in `vader.json`" means the driver discovers registered generators and runs them without the user writing the loop: a manifest key naming the generator modules, plus a default metaprogram that walks them. Decide what it can express (all structs of a module? a selector? ordering between two generators that touch the same module?) before designing the key.
  - **Opt-in granularity is open, and `@derive(json)` is only one candidate** (user is unconvinced by it, 2026-08-27). Options, with what each costs today: **(a) selection in `build.vader` / `vader.json`**, by module, by a list of type names, by a predicate the driver writes; **needs no language change at all**, and it IS the plug-and-play surface, so it is the default until something forces more. **(b) a decorator**: `@derive("json")` is `R2010` today because the whitelist is closed; measured that with a **string** argument the name is the only obstacle, the identifier-resolution half disappearing in that form. Presupposes per-declaration opt-in is wanted, which is exactly what is not settled. **(c) a marker trait**, attractive because it uses existing surface, but ⚠️ **not expressible today**: `Point implements Json {}` on a zero-method trait is `R2016` ("short impl form requires a trait with exactly one method"), and a *default* method still counts as 0 *required* ones, so a marker would need a required method written per type (boilerplate that defeats the purpose) or a language tweak allowing an impl of a marker trait. Decide the granularity before the mechanism.
  - **It also collides with an open architectural question**: whether a derive handler runs in the comptime VM or as compiler code. A library-shipped generator imported by a `build.vader` is squarely the second answer, so choosing plug-and-play largely settles it.

- [ ] **`JsonValue` has no `Display`** (noted 2026-10-21). `${json}` is T3018, and `stringify` (`lib/json/json.vader`) is the only spelling. A union dispatches through a trait all its variants implement (ADR 0047), so one `Display` impl per variant makes `${json}` work with no compiler change.

- [ ] **`Path`, `Duration` and `Monotonic` print through their backing type** (noted 2026-10-21). `${d}` on a `Duration` gives `1500`, with no unit. A `Display` of their own waits on « A boxed distinct loses its own `Display` » above: interpolating an `X | null` whose distinct has one is T3086. `Path.as_string` (`lib/std/path/path.vader`) stays until then.

- [ ] **`std/bignum` (`BigInteger` / `BigDecimal`**) arbitrary precision. Use cases : JSON parsing without precision loss past 2^53, money/financial DSLs, crypto bignums. Pure Vader ~600-1000 LoC each. BigInteger first.

- [ ] **`std/encoding` over `Buffer`: the consumer the multi-byte memory opcodes are waiting for** (noted 2026-07-27). `LoadI32`/`I64`/`F64` and their `Store*` twins are implemented end to end, VM (`vm/exec.vader`), C emit (`emit/c/walker.vader` → `vader_buffer_load_i32`), dump, `.virt` reader, but NOTHING can mint them: a memory op only comes from a mangle match in `midir/select/intrinsics.vader`, and `std/core/buffer.vader`'s `ByteAccess` declares only `load_u8` / `store_u8` / `memory_copy` / `intern_string` / `write_string`. They are an ABI landed ahead of its surface; do not prune them as unreachable (an audit nearly did). Two constraints to settle before exposing anything:
  - **Name the endianness** (`load_i32_le` / `_be`), never leave it "native". WASM defines its linear memory little-endian NORMATIVELY, while the C backend's `memcpy` follows the machine, so a single "native" accessor means two different things across backends on a big-endian target. An explicit `_le` is one instruction on both (`i32.load` / `memcpy`).
  - **`_be` is cheap natively, expensive in WASM**: `__builtin_bswap32` is one instruction, but WASM has NO byteswap instruction, so it costs shifts + masks, roughly what the existing pure-Vader shift loop costs. Consequence for the obvious candidates: MD5 (little-endian) would gain on both backends, **SHA-256 (big-endian) gains nothing in WASM**. Measure before promising a crypto speed-up. Note also that `crypto.vader` works on `u8[]`, not `Buffer`, so it would first have to move onto a `Buffer`.
  - Reference implementation of the byte semantics already exists in `vader/core/bytecode/byte_codec.vader`, which explicitly names `std/encoding` as its successor, and which cannot itself use the opcodes it implements.

- [ ] **`std/cli`: subcommands** (lib `lib/cli/`). The declarative `FlagSpec` parser, generated help, long + short aliases and the rejection of unknown `-x` tokens have landed, and `vader/tools/cli` runs on them. Still missing: first-class subcommands, so each CLI keeps dispatching on the first positional by hand.

- [ ] **Example `aoc_2024_day1`**: a small program validating I/O + parsing + collections end to end, alongside `examples/`.

- [ ] **std/iter: the lazy combinators still missing** (noted 2026-10-02). Simple generators written like `indexed`, no blocker: `map_not_null`, `take_while` / `skip_while`, `first() -> T | null`, `distinct_by`, `min` / `max` / `min_by` / `max_by`, `scan`, `flatten`, `on_each`. `filter_is<U>()` waits on the `x is U` miscompile (Priority).

- [ ] **`read_file_string` refuses an ordinary data file past 16 MiB by default** (noted 2026-10-15, user request). `read_file_string(path)` defaults `max_bytes` to `READ_LIMIT_DEFAULT`, so a 23.7 MB JSON file comes back as `IOError { .msg = "file too large" }`. The ceiling is right for a stream (the `read_file_bytes` doc says why) and its value is set by the VM (the `READ_LIMIT_DEFAULT` doc). Lifting it for regular files alone only moves the failure: native has a heap cap too (`VADER_GC_OLD_MAX`, `runtime/c/vader.h`) and `vader_gc_alloc` traps once it is exhausted, so a large enough file would die in the GC on native as a 256 MiB one does on the VM.
  - **General fix: one bound derived from the heap, for every input.** A fallible grow (`try_reserve`, over the NULL-returning `vader_old_alloc` that the trap wraps) or a `gc_headroom()` intrinsic, which the VM host divides by its per-byte cost. One rule for pipes, regular files and both backends; `max_bytes` stays the caller's own policy. Costs a runtime function and an `@intrinsic` (two commits, for the seed).
  - **Then, an optimisation: size the buffer from the open file.** `fstat` on the handle (`GetFileType` / `GetFileSizeEx` on Windows; `sys_path_kind` answers the kind, but by path and before the open), then `out: u8[]: [] * (size + READ_CHUNK)` instead of growing by doubling through `push_all`: for 23.7 MB that saves about 32 MiB of copies and drops the peak from about 3x the content to 1x, the peak that trips the VM first. Keep looping to end of file (a file can grow, Linux `/proc` files report a size of 0). This is the file-size query that the §3.7 item "Rethink the portable API and the FFI for multiple targets" says `std/io` lacks.
  - **The VM's one boxed slot per byte** is the packed-storage question already tracked in §3.7 ("The VM's `ArrayVal` storage as a union", ADR 0029). It raises the VM's threshold to native's; it does not remove the trap.
  - **The message** should name the bound that was hit: `max_bytes` (and how to raise it), or memory, where "pass a larger `max_bytes`" would be wrong advice. Secondary: `bytes_to_string` interns the whole file once more (hash and copy in `vader_atom_intern`); an adopt-buffer entry would avoid it.

- [~] **Self-host typecheck working-set reduction** (profiled 2026-05-25). `VADER_GC_PROFILE=1 ./build/vader dump --stage=typed-ast vader/tools/cli/main.vader` over the full self-host project (170+ modules transitively imported) reports an **81 MB live set** dominated by :
  - `vader_diagnostics_Position` (48 B × 345k = **16.5 MB**): 16 B header + 16 B `file: string` + 16 B (offset / line / column).
  - `vader_diagnostics_Span` (64 B × 240k = **15.4 MB**): each holds two `Position` refs.
  - `ARRAY_BUF` (15.4 MB): variable-sized array storage.
  - `std_collections_Entry(Any, Any)` (72 B × 132k = **9.5 MB**): sum of every `MutableMap` entry across `TypedProgram` side-tables, `ResolvedModule` maps, and comptime/lower internal tables. After erasure-dedupe (`b528d2bc`, `b85f1ce5`) all `MutableMap(K, V).Entry` variants collapse to a single C type at codegen, so every map entry shows up under one index. The count is real data, not erasure-dedupe overshoot.

  Two parallel work-streams to reclaim memory :

  **(I) String interning, ✅ shipped 2026-05-25**: every `string` became a 4 B atom id ([ADR 0109](./docs/adr/0109-a-string-is-an-atom.md)).

  **(II) `MutableMap` entry footprint: ~5 MB.** Three orthogonal pistes :
  - **(a) Flat `Type[]` for dense int-keyed maps**: `decl_types : MutableMap(i32, Type)` is keyed by `Symbol.id`, minted sequentially → quasi-dense. Replace with `Type[]` indexed by id : ~17k symbols × 8 B ref slot = ~136 KB vs 17k entries × 72 B = ~1.2 MB. Saves ~1 MB and turns the lookup into O(1) array-get (no hash). Most-consulted side-table per resolve, so latency win on top of memory. Applies similarly to `struct_decls`, `trait_decls` (also `Symbol.id`-keyed). Touches `vader/front/typecheck/typed_ast.vader` + every reader. ~½ day.
  - **(b) Fuse the three `Type`-by-int side-tables**: `expr_types: MutableMap(usize, Type)`, `local_types: MutableMap(i64, Type)`, `type_expr_types: MutableMap(i64, Type)` all store `Type` keyed by a numeric id. One `MutableMap(i64, Type)` with the discriminator packed into the key (top 2 bits = source family) halves the bucket count and the Entry allocations. Estimated ~3 MB saved if these three account for ~half the 132k entries. Touches all callers ; needs an accessor layer to keep the readers explicit about which family they're querying. ~1 day.
  - **(c) Specialised `IntMap(V)` stdlib type**: `MutableMap` keys go through `key: Any`, paying 16 B per entry even when the source type is `i32` / `i64` / `usize`. An `IntMap(V) :: struct[V]` storing `key: i64` raw (8 B) saves 8 B × ~80k int-keyed entries = ~640 KB. New stdlib struct in `stdlib/std/collections/`. ~1 day including tests.

  **(III) Flatten `Position` into `Span`: ~16 MB (subsumes part of (I)).** Open architectural choice. Span becomes `{ file_id, start_offset, start_line, start_col, end_offset, end_line, end_col }` inlined ; kills the 345k Position heap allocs entirely (their headers alone are 5.5 MB). Larger refactor: touches every span-construction site across the parser, typecheck, lower, diagnostics. Synergy with (I) Phase 1 : do them together once Atom is in place. To document if pursued.

### 3.8 Language ergonomics
- [~] **`defer` unwinds on panic** (gap surfaced 2026-05-19): **VM DONE, C target pending.** Defers lower to per-frame `DeferPush` / `DeferPopExec` ops; on a trap the **VM now walks frames bottom-up and drains each frame's pending defers before propagating** (`vader/vm/exec.vader:1008`). Remaining (re-checked 2026-10-25): natively, `vader_trap` and `vader_panic` now drain the defer stack before `abort()`, but `vader_unreachable` (`runtime/c/vader_runtime.c`) still aborts without it, where the VM unwinds on every trap. The compiler emits `unreachable` for failures a program can meet (a singleton called while it initialises, an async `main` left suspended, a trait call no dispatcher case covers), so those skip the defers natively; draining in `vader_unreachable` too would close it. Same fix unlocks a future `recover` / `rescue` primitive. Cross-ref §3.1 Concurrency (panic propagation across spawned tasks).
- [ ] Static-size arrays `[T; N]`.
- [x] **Which integers may index** (idea, 2026-10-14 ; settled 2026-10-19 by direction (3) : an index is any integer and a length an `i64`, ADR 0093 and 0094 ; `xs[-1]` counting from the end is planned). Since ADR 0061 `s[i]` takes the `usize` key of its impl, so `s[idx]` with an `i32` is T3001, while an array still takes any integer. Three directions: (1) `i32 implements Into<usize>`, which would convert at every `usize` slot, not only at an index, and must trap on a negative; (2) negative indices count from the end (`xs[-1]`), which needs a signed key, puts a branch in every access whose index is not known non-negative, and turns an off-by-one into a silent read of the last element; (3) drop `usize` from the surface and index by a signed integer, a charter-level change (bounded integers would let an `i32` known `>= 0` reach a `usize` slot). Decide together with the charter's bounded-number steps.
- [ ] **Too many ways for a `match` to leave a variant out** (idea, 2026-10-19, to revisit together). Three forms overlap. A plain `match` must be exhaustive (T3013); a `_` arm lifts that, and on a closed union in value position earns W0005. `@partial` lifts both T3013 and W0005. `@unreachable` lifts T3013 and promises the uncovered variants never come. Read against the code, they reduce to fewer ideas than they suggest:
  - `@partial` with no `_` arm already traps on an uncovered variant. `lower/match.vader` gives every match the same `LoweredUnreachable` fallback, and only its message tells the two decorators apart. So `@unreachable` is `@partial` without a `_`, plus a stated intent.
  - `@partial` with a `_` arm is a plain `_` arm minus W0005: there the decorator is a lint suppression.
  - `_ -> unreachable("why")` (`std/abort`, `@no_return`) already says "the rest cannot happen", with its reason in the code rather than in the `// @partial:` comment the style guide asks for. No arm in the tree uses it today.

  The real questions are two: does the match have a catch-all, and does the author vouch for it on a closed union. Counts today: 141 `@partial match`, 5 `@unreachable match` (`front/typecheck/narrow_value.vader`, `front/typecheck/range_ops.vader`) plus the `match_partial` snippet. Nothing decided: keeping one decorator, keeping none (the impossible case written `_ -> unreachable(…)`) and where W0005's opt-out would then live are all open. Touches SPEC §12, the decorator table of the style guide, T3013, W0005 and W0014.

- [ ] **An inverted range pattern draws no warning** (surfaced 2026-07-24 reviewing range-patterns). `'z'..='a'` (lower > upper) lowers to a statically never-true `>= 'z' && <= 'a'` with no warning; Rust warns. Cheap constant-fold check (both bounds are required literals), but a new warning code, listed in SPEC §Patterns.
- [ ] `@derive(Eq, Display)` to auto-generate trivial impls.
- [ ] **Function overloading by full signature** (post-MVP elevation of receiver-only overloading): pick the candidate whose *all* parameter types match. Generalises the resolver's overload table + typechecker's call resolution.
- [~] **Generator functions (`@generator` + `yield`), lazy element-by-element iteration.** **Phases 0-4 LANDED 2026-07-01**, the feature is functionally complete for v1 (non-generic / concrete-element generators). Surface (`yield` keyword + `YieldStmt` + `@generator`), typecheck (T3056–T3061), and the state-machine lowering (`vader/lower/generator.vader`: spill params+locals into a synthesized `g$State`, route refs to `self.<field>`, block-split the body into a `loop { if state==k … }` `Iterator::next`) all run correctly on **both backends** for straight-line yields, single + nested loops, break/continue across a yield, yield-in-if/match, and struct element types. Feature snippets `generator_{basic,nested,filter,break,struct_elem}` + LSP `YieldStmt` arms. `verify.sh` green throughout, suite 2493/0. **Remaining (`[~]` → Phase 5, DEFERRED):** dogfood on hot self-compile paths, generic generators (blocked on the pre-existing erased-generic vtable gap), and fusion/caller-monomorphization: all gated on Couche 4 of the stream-fusion item below (the erased `next()` is a per-element virtual call). Below is the original design note.
  ```
  @generator
  concat_file_decls :: fn(files: SourceFile[]) -> Iterator<Decl> {
      for f in files {
          for d in f.program.decls { yield d }
      }
  }
  ```
  **Resolved:** the Phase-0 cascade spike chose approach **B** (an AST/lower desugar to a `loop { match state }` state machine, synthesized as a `LoweredLoop` + `i32` if-chain since there's no `LoweredMatch` node) and validated its output shape on both backends before implementation. Perf (per-element virtual dispatch on the erased `Iterator<T>`; fusion + caller-monomorphization) and migration (callers needing `.len()`/indexing break; audit before converting) remain the deferred Phase-5 work.
- [~] **Stream-fusion generalization: lazy iterator chains → the eager loop** (perf). Both the eager combinators (`arr.map(f).filter(p)` = a throwaway array per stage) and the lazy ones (`MappedIterator`/… = a tower of erased trait-object iterators, virtual `next()` + boxed `Yield<T>` per element under erasure) collapse to one flat loop via fusion. `try_lower_chain_fusion` (`vader/lower/for_in.vader:889`) already does this but ONLY for int-range sources, `map`/`filter`, and `for-in` terminals. Widen it: Couche 1 array/string/map-set sources (+ a concrete `arr.iter()`, none exists today, only erasing `.into()`), Couche 2 `take`/`skip`/`enumerate`/`flat_map`, Couche 3 recognize `.collect()`/`.count()`/`.any_match()`/`.fold()`/… terminals at the call site (synthesize their accumulation as the fused body), Couche 4 inline `@generator` yield-loops. Independent of generators for Couches 1-3 (bulk of the win); Couche 4 + the combinator-struct→`@generator` rewrite (Tier 1: Mapped/Filter/Take/Skip; Tier 2: Map/Set near-vestigial; Tier 3 keep ArrayIterator/StringChars as primitives) come after generators. Enablers: `arr.iter()`, harden generic-HOF lambda inference (works-but-untested + silent mistype today), explicit concrete chain heads for Map/Set/String (UFCS Into gate is array-only). Measure alloc volume, not RSS (short-lived allocs = profiler blind spot).

- [ ] **`std/iter` has no `min` / `max` terminal** (noted 2026-10-21). A generic default-init is no longer the blocker: `sum<T: Add & Zero>` starts from `T.zero()`. `min` / `max` need none, since they return `T | null` on an empty source.
- [ ] **Common-field access on unions (methods**) extend to UFCS calls (`e.method()` valid when every variant has a callable `method`). Invasive: overload resolution × variant set.
- [ ] **Common-field access on unions (nullable receivers**) `(T | null).f` follows the gate today (`null` lacks the field → T3009). Decide whether to special-case optional chaining; `??` already covers the common case.
- [ ] **AST node id boilerplate**: re-audited 2026-05-15 ; deferred. ~11 self-host fields carrying `id: UNASSIGNED_NODE_ID`. All three resolution shapes (decorator, mixin, marker) need new compiler infrastructure that's bigger than the 128 lines it would save. Revisit if decorator infra lands for other reasons.
- [ ] **A bare identifier in a `match` pattern BINDS, it does not compare** (noted 2026-09-05).
  ```
  K: i32: 7
  match 99 {
      K -> "matched K"      // taken, for every value
      _ -> "fell through"
  }
  → matched K
  ```
  `K` is a binding pattern that shadows the constant, so the arm is irrefutable and every later arm is dead. It compiles clean. The only hint is `W0007 K is never used`, which does not appear at all once the constant has another user, which is exactly the case for a table of named platform codes.
  Found writing `std/io::last_io_error`, where a `match` over `ENOENT` / `EACCES` / `EISDIR` classified all three as the first arm. The codes were right and the classification silently was not; both bodies are `if` chains now, with the reason written beside them.
  Rust hit the same shape and answered with a lint (`bindings_with_variant_name`, deny-by-default) plus the convention that a const pattern is a PATH. Options here, roughly in order of cost:
  - warn when a binding pattern's name resolves to a module-level constant in scope: the narrow, high-value case, and what actually bit;
  - require a leading `.` or a qualified path for a value pattern, making a bare name unambiguously a binding (a syntax change, SPEC §"Patterns");
  - leave it, and rely on `_` never being reached being caught by T3013, which it is NOT here, since the first arm covers everything.

- [ ] **Memory ops map 1:1, but pin down endianness and `align`** (noted 2026-07-27). The whole `Load*` / `Store*` / `MemoryCopy` family has a direct WASM counterpart (`i32.load8_u`, `i32.load`, `i64.store`, `f64.load`, `memory.copy`), and WASM permits UNALIGNED access, which matters since a `Buffer` offset carries no alignment guarantee. Two decisions for the emitter: (a) WASM memory is little-endian by spec while the C backend follows the machine, so the two backends only agree as long as no big-endian target exists, which is an argument for naming endianness in the stdlib surface rather than in the opcode (see `std/encoding` under §3.4); (b) what to put in each `memarg`'s `align`: 1 (always safe, possibly slower) or derived from the offset when statically known.
